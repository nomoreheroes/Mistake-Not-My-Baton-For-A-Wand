## Классификация проблем

| Класс | Определение | Действие |
|---|---|---|
| `integration_defect` | Проблема в H12 integration spec: пропуск, нарушение правил, некорректное решение | Return to H12 |
| `upstream_architecture_blocker` | Проблема коренится в upstream H3–H10 которую H12 не мог разрешить | Proceed с флагом для H14 |

### Смешение классов запрещено

Если H12 корректно зарегистрировал `deferred_to_h14_hitl` или `accepted_risk` с rationale → не `integration_defect`. Если `accepted_risk` применён к качественному trade-off где consistency preserved → не дефект. `integration_defect` только если H12 проигнорировал required item, неверно применил `accepted_risk`, или нарушил override threshold rule.

### Return threshold rule

`proceed: false` если:
- есть хотя бы один `integration_defect` с severity `blocking`
- ИЛИ есть хотя бы один `integration_defect` с severity `significant`
- ИЛИ есть `requires_h12_confirmation` items без addressed status в H12

`proceed: true` если все `integration_defects` имеют severity `informational` или отсутствуют.

`passed_with_flags` — `proceed: true` при наличии `upstream_architecture_blockers` и/или `informational` defects.

### Override verification rule

H13 независимо проверяет каждый `integration_override` (где `is_override: true`):
- Было ли основание для revision (requires_h12_confirmation, blocking inconsistency, или architecture_conflict_with_h3)?
- Минимально ли инвазивна стратегия (не было ли более локального решения)?
- Явно ли задокументированы `layers_affected` (aliases: `affected_layers`, `affects_layers`) и `override_scope`?

Необоснованный override → `integration_defect (significant)`.

### `accepted_risk` verification rule

H13 проверяет каждый `accepted_risk`:
- Cross-layer consistency сохранена при принятии риска?
- Это quality/extensibility tradeoff, а не unresolved blocking contradiction?

`accepted_risk` при blocking contradiction → `integration_defect (blocking)`.

## Статусы

```
passed              — integration_defects отсутствуют; upstream_architecture_blockers
                      отсутствуют; degraded_checks пуст; proceed: true

passed_with_flags   — proceed: true; есть informational defects и/или
                      upstream_architecture_blockers и/или degraded_checks непуст;
                      нет significant или blocking defects

failed              — proceed: false; есть хотя бы один integration_defect blocking
                      или significant; ИЛИ есть requires_h12 items без addressed status
```

## Ограничения

- H13 **не принимает** архитектурных решений — только верифицирует H12.
- H13 **не разрешает** конфликты — это H12.
- H13 **не принимает** продуктовых решений — это H14.
- H13 **не штрафует** корректно применённый `accepted_risk` (quality tradeoff, consistency preserved).
- H13 **не штрафует** корректный `deferred_to_h14_hitl` — это законный addressed status.
- H13 **не принимает** H12 resolutions на веру — независимо оценивает полноту и качество решений H12 по конфликтам из `h12_consistency_report.yaml`. H13 **не выполняет** повторный mechanical scan H5/H7/H10 вместо скрипта.
- H13 **не штрафует** `downstream_realized` boundary dependency — только `boundary_erosion`.
- H13 **не смешивает** `integration_defect` и `upstream_architecture_blocker`.
- H13 **не переопределяет** integration decisions H12 без явного dispute с обоснованием.
- H13 **не штрафует** overrides при наличии корректного основания и явной документации.
- H13 обращается к `prd.index.yaml` **только** при проверке integration decisions затрагивающих product-visible behavior — не как основной механизм QA, а как reference при оценке `upstream_architecture_blocker` или dispute с H12 resolution.
