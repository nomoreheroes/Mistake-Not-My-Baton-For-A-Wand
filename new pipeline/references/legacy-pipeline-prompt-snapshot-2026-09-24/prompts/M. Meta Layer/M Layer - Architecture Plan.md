## 0. Предусловия (обнаружены при обследовании репозитория, не предположения)

Мета-слой по своей природе — надстройка над уже существующими слоями A–J. Он не может быть спроектирован в вакууме: его механика напрямую зависит от того, что уже реально работает в репозитории. Обследование дало три факта, которые формируют ограничения ниже.

**Факт 1 — два независимых git-репозитория.**
```
c:\Projects\software_workflow\.git            — пуст (0 коммитов, нет HEAD/refs/objects)
c:\Projects\software_workflow\TEST WORKFLOW\.git — рабочий, 10 коммитов (I-слой и ранее)
```
Промпт-файлы (`A. Idea Note Layer\*.md`, `J. Implementation\*.md` и т.д.) и Architecture Plan-документы лежат в **корневом** репозитории — который сейчас не версионирует ничего. Артефакты пайплайна (`TEST WORKFLOW\*\`) лежат во **вложенном** репозитории, который уже используется для коммитов.

**Следствие:** Step 0 алгоритма из ТЗ («откатываем git на состояние до запуска проблемного промпта») физически требует отката **артефактного** репозитория (TEST WORKFLOW) до входного состояния промпта, при этом сам текст промпта редактируется в **отдельном, невложенном** репозитории. Это не один откат, а два скоординированных отката в разных репозиториях — см. §6.

**Предусловие P1 (блокирует полноценную работу M-слоя, не блокирует написание плана):** корневой репозиторий должен быть инициализирован и промпт-дерево закоммичено (минимум: baseline commit перед первым запуском M-слоя). Без этого у M1 нет опорной точки для «git_checkpoint.before_prompt_edit» (§6.2). Рекомендация лежит в §14.

**Предусловие P2:** коммиты в `TEST WORKFLOW/.git` на сегодня зернистые — «Run I21 full task specs (185 tasks)» покрывает много агентских запусков одним коммитом. Точный откат «до запуска одного промпта» невозможен, если это не был отдельный коммит. M-слой должен уметь работать в двух режимах точности отката: `commit_level` (если запуск проблемного промпта — целый коммит или коммит найден по grep) и `manual_diff_level` (если коммит смешанный — M1 запрашивает у человека вручную указать, какие файлы/поля относятся к проблемному запуску, и делает частичный `git checkout <commit>~1 -- <paths>`). Это честнее, чем предполагать несуществующую гранулярность.

**Факт 2 — все слои A–J являются HITL-сессиями Claude Code, а не автономными демонами.** (Подтверждено J-слоем R13: «J-runner отдельно не существует».) Значит, «мета-слой запускается» всегда означает: человек-оператор стартует M1 как отдельную (или вложенную) Claude Code сессию — автоматического фонового триггера нет и не должно быть. M-слой формализует **что** передавать M1 при старте (структурированный `meta_trigger_signal.yaml`), а не пытается сам себя автоматически инициировать.

**Факт 3 — паттерн `upstream_resync` уже существует в G/H-слоях** (см. G9/G10 execution state в памяти: «revision_kind: upstream_resync»; H-слой: `hX_revision_request.yaml`). Это значит, что механизм «пересчитать даунстрим после того, как апстрим-артефакт задним числом изменился» **уже реализован в каждом слое отдельно**. M-слою не нужно изобретать собственный каскадный пересчёт — он обязан переиспользовать существующий resync-протокол каждого слоя (§7). Это ключевое архитектурное решение этого плана.

## 1. Назначение слоя

M-слой — не слой продукта. Он не производит артефакты для B/C/D/.../J. Он работает **над** пайплайном A–J: диагностирует и чинит промпт-файлы (`*.md` агентов) и документы архитектуры (`* Layer - Architecture Plan.md`), когда пайплайн ведёт себя неправильно, а также проактивно ищет возможности для улучшения — либо через ретроспективу целого слоя, либо через случайный точечный аудит одного промпта.

**Область действия (уточнено R3, закрывает W-1):** М-слой правит/аудирует промпты и Architecture Plan-документы слоёв **A–J** — это единственный объект правки на сегодня. Собственные промпты M1–M8 подлежат тем же механизмам (`random_audit`, `layer_retrospective`, §5.9/§10/§11), но это отдельный, самостоятельный предмет аудита, а не расширение зоны правки на «A–M»: упоминание в §10 (glob по `[A-M]`) относится именно к возможности аудировать M-слой сам себя, не к тому, что M-слой правит нечто за пределами A–J. K-слой (аудит и документация, DRAFT R1 на 2026-07-03) в объём этого плана пока не входит — будет учтён после финализации K-плана (ожидается R5 K-плана); открытый вопрос — есть ли у K собственный `upstream_resync`-подобный протокол для §7, или M-слою придётся для K сделать исключение.

```
Вход в M-слой:                                  Выход из M-слоя:
- meta_trigger_signal.yaml (кто/что/почему)      - изменённый промпт-файл (если применимо)
- целевой слой / целевой агент / случайная       - обновлённый Architecture Plan слоя (если применимо)
  выборка                                        - m_layer_session_summary.yaml
                                                  - meta_layer_prerequisite.yaml (0..N, для похожих промптов)
```

M-слой **никогда** не редактирует:
- сгенерированные данные-артефакты в `TEST WORKFLOW/*` (это данные, а не код процесса; они пересчитываются повторным запуском исправленного промпта через собственный resync-протокол слоя — §7);
- код продукта, производимый J-слоем;
- `pipeline.db` / `causal_graph.db` / `tasks.db`.

M-слой редактирует только: промпт-файлы агентов, Architecture Plan-документы слоёв, собственные мета-артефакты и собственный тестовый корпус (§6.1).

## 2. Триггеры мета-слоя

### 2.1 Четыре макро-триггера (`trigger_mode`)

```
reactive_fix          — пайплайн отработал очевидно неправильно; нужно чинить сейчас
layer_retrospective   — целый слой пайплайна завершился (gate: true); анализ + поиск оптимизаций
random_audit          — случайно выбранный промпт из всего пайплайна; точечный аудит без предполагаемой поломки
prerequisite_check    — (R3, закрывает S-1) отложенная проверка meta_layer_prerequisite.yaml
                        (Step 4, §9.10) перед реальным запуском промпта, для которого ранее
                        был найден подозреваемый аналогичный паттерн в другом промпте; нет
                        инцидента, нет отката — см. §2.4
```

Все четыре — **человеко-инициированные** (см. Факт 2, §0). `meta_trigger_signal.yaml` — структурированная форма того, что человек (или агент/оркестратор, заметивший проблему в ходе своей сессии) передаёт M1 при старте.

### 2.2 Реактивные паттерны внутри `reactive_fix` (`reactive_pattern`)

Из ТЗ, формализовано:

```
upstream_return_misunderstood
  — downstream вернул управление в upstream (revision_request-подобный артефакт),
    но upstream агент не может его обработать: не находит нужную секцию в своём
    промпте, формат не совпадает с ожидаемым, или промпт вообще не содержит
    правила обработки возврата.

loop_exceeds_threshold
  — цикл downstream→upstream→downstream повторился > 3 раз для одной и той же
    пары агентов по одному и тому же артефакту. Означает рассинхронизацию
    контракта между двумя промптами, а не разовую ошибку исполнения.

qa_found_prompt_attributable_defect
  — QA-агент нашёл дефект в работе проверяемого агента, И этот дефект
    прослеживается к формулировке промпта (двусмысленность, отсутствующее
    ограничение, противоречивая инструкция), а не к разовой вариативности
    исполнения LLM.

schema_mismatch_detected
  — промпт-оркестратор текущего слоя выполнения (не человек, не QA-агент)
    в процессе подготовки хендоффа между двумя агентами замечает, что
    схема выходных артефактов одного промпта не совпадает со схемой
    входных артефактов, ожидаемой следующим промптом/слоем — т.е.
    обнаруживает баг пайплайна напрямую, по факту статического
    несоответствия контрактов, ещё до того, как это привело к сбою
    исполнения или к циклу возвратов (который ловит loop_exceeds_threshold).
    detected_by в этом случае — сам оркестратор (см. §9.1), а не человек
    и не находка QA-агента на готовом артефакте. Механика материализации
    сигнала оркестратором — §12, п.3 (R3).
```

### 2.3 Что НЕ является триггером (фильтр шума)

Это важное уточнение, которого не было в исходном ТЗ, но необходимое: в текущем пайплайне `status: failed` на QA-гейте — **штатная, ожидаемая часть Maker-Checker цикла** (H4 упал 2 раза, G-слой находил дефекты десятками — это видно в памяти проекта). Если триггер 3 (`qa_found_prompt_attributable_defect`) срабатывал бы на любой `failed`-вердикт, M-слой запускался бы после почти каждого QA-гейта во всём пайплайне — это шум, а не сигнал.

**Правило:** `qa_found_prompt_attributable_defect` фиксируется только тогда, когда человек-оператор (или сам QA-агент в своём отчёте, если явно обучен это отмечать) классифицирует дефект как **системный** — то есть промпт maker-агента структурно приглашает эту ошибку (например, инструкция сформулирована так, что почти любой запуск получит тот же дефект), а не как **вариативность одного прогона**. `revision_request.yaml` с обычным списком find/fix — это здоровая работа слоя, не повод для M-слоя.

Аналогично `loop_exceeds_threshold` считается не по любому возврату, а по счётчику именно между **одной и той же парой** агент↔агент по **одному и тому же артефакту**. Определение счётчика — §5.2.

**Исключение из правила накопления:** `schema_mismatch_detected` — единственный из четырёх паттернов, который срабатывает по единичному факту, без накопления повторов и без классификации человеком/QA. Это осознанно: несоответствие схемы выход-агента N ↔ вход-агента N+1 — структурная, а не вероятностная поломка (в отличие от variability одного прогона LLM); если оркестратор его увидел один раз, оно не «рассосётся» само на следующем прогоне — контракт либо совпадает, либо нет.

**Эмпирическая операционализация (R3, дополняет правило выше):** классификация «системный vs разовый» не обязана оставаться чисто субъективным суждением человека/QA — она может быть **подтверждена стохастическим Tier 2-тестом** (§5.6): дефект воспроизводится в ≥k из n прогонов golden input → `qa_found_prompt_attributable_defect` подтверждён как системный; воспроизводится реже — `transient_execution_error`. Порог k/n — параметр (default 2/3, см. OQ-M-006). Суждение человека остаётся допустимым и достаточным путём классификации там, где тест недоступен (напр. HITL-агенты, §5.6.2) — тест предпочтительный, не обязательный путь.

### 2.4 `trigger_mode: prerequisite_check` (R3, закрывает S-1)

Ранее план предполагал (было в §9.7), что перед запуском агента с `meta_layer_prerequisite.yaml.status: pending` оркестратор слоя обязан «сначала прогнать M-слой в режиме reactive_fix (proactive-вариант)» — но `reactive_fix` по определению предполагает инцидент, и его контракт (precision отката P2, evidence из сбоя) не подходит для ситуации, где инцидента ещё не было. R3 вводит отдельный `trigger_mode`:

```
Семантика:
  - Нет инцидента, нет evidence сбоя, нет отката (P2 не применяется).
  - Вход: prerequisite_ref: MLP-{seq} (см. §9.10) вместо evidence_refs.
  - M2 работает в текстовом режиме: анализирует suspected_pattern против
    реального текста промпта-кандидата, БЕЗ rerun-механики (rerun появится
    позже, естественным путём, если гипотеза подтвердится и заведётся
    полноценный reactive_fix).
  - Исход: либо подтверждение (root_cause_class как в обычном reactive_fix,
    дальше по FSM §5 с шага specifying — architecting пропускается, если
    решение уже понятно из аналогичного фикса) либо false_positive
    (см. §5.1, §9.2) — meta_layer_prerequisite.status → consumed_false_positive.

Preflight M1 (§4.1, п.3): для prerequisite_check шаг определения precision
отката (commit_level | manual_diff_level) ИСКЛЮЧАЕТСЯ — отката не будет,
пока не заведётся отдельный reactive_fix по факту реального инцидента.
```

Контракт §9.10 (было §9.7 в R1/R2) переписан с `reactive_fix` на `prerequisite_check` — это была прямая несостыковка предыдущих ревизий, а не преднамеренное решение.

```
           │ Tier 2 golden/стохастически)
           ↓
   M8 Documenter: обновляет Architecture Plan слоя, финализирует
   тестовый корпус (§6.1), пишет m_layer_session_summary.yaml, ищет
   аналогичный паттерн в других промптах (Step 4) → meta_layer_prerequisite.yaml (0..N)
           ↓
   Отчёт человеку: что исправлено, что смёржено (включая тесты), какие
   слои уведомлены о предварительной проверке при следующем запуске
```

## 4. M1 — Meta-Dispatcher

M1 — единственная точка входа, аналогично J0: один агент-оркестратор-исполнитель в рамках интерактивной сессии, вызывает M2–M8 как subagents через Agent tool, выполняет git-операции через bash.

### 4.1 Алгоритм M1

```
1. Если meta_trigger_signal.yaml не передан — интервью человека, создать его (§9.1),
   либо прочитать черновик из inbox/ (§12, п.3), если он там есть
2. trigger_mode = meta_trigger_signal.trigger_mode
3. Preflight (общий для всех режимов):
   • корневой репозиторий инициализирован? (см. P1, §0)
     – нет → СТОП, сообщить человеку: нужен минимум baseline commit промпт-дерева
   • crash-recovery (R3, §4.3): есть осиротевшие .m-worktrees/*, .m-verify-worktrees/*
     или ветки m/* от незавершённых сессий (по m_session_state.yaml без терминального
     статуса)? → предложить человеку resume | abort-с-очисткой, ПРЕЖДЕ чем создавать
     новую рабочую область
   • конкурентная сессия (R3, закрывает Minor 4): найден второй m_session_state.yaml
     без терминального статуса, ОТЛИЧНЫЙ от той сессии, что человек сейчас пытается
     запустить/возобновить → СТОП, спросить человека явно (meta_session_log.yaml,
     §9, предполагает одну активную M-сессию)
   • для reactive_fix: определить precision отката — commit_level | manual_diff_level (P2)
   • для prerequisite_check (R3, §2.4): шаг определения precision отката ПРОПУСКАЕТСЯ —
     отката не будет
4. Ветвление по trigger_mode:
   a) reactive_fix        → §5 (Протокол исправления)
   b) layer_retrospective → §11
   c) random_audit        → §10
   d) prerequisite_check  → §2.4, далее §5 с шага specifying (M4), если гипотеза
      подтверждена; иначе завершение с outcome: no_action_needed
5. M1 создаёт/переиспользует изолированную рабочую область:
   .m-worktrees/{session_id}  (корневой репозиторий, для промпт-файлов и тестов)
   branch: m/{session_id}/{slug}
   M1 инициализирует/обновляет m_session_state.yaml (§4.3) на каждом переходе автомата
6. По завершении: m_layer_session_summary.yaml, отчёт человеку, merge-инструкция
   (см. §6.4 — M1 не мержит в основную ветку без явного подтверждения человека,
   т.к. это правка процесса, а не рутинный коммит)
```

### 4.2 Изоляция

Как и J0, M1 не работает напрямую в основной ветке корневого репозитория:

```
.m-worktrees/{session_id}      ← правки промпт-файлов и тестов только здесь
branch: m/{session_id}/{slug}
```

Запрещено (в основном checkout корневого репозитория): `git commit`, `git reset --hard`, `git checkout -- .`, `git clean`.

Отдельно, для верификационных прогонов (Step 2) — изолированный **артефактный** worktree в TEST WORKFLOW/.git:

```
TEST WORKFLOW/.m-verify-worktrees/{session_id}  ← проверочный прогон исправленного промпта
```

Эта область **не трогает** реальный прогресс слоя, который мог уйти дальше по времени, чем момент бага (см. §6.3).

**Параметризация корня артефактов (R3, закрывает S-2b):** любой subagent, запускаемый M1 против verify-worktree (§6.3) или против golden input теста Tier 2 (§5.6), получает явный параметр корня артефактов (переопределение через env-переменную или подстановку в промпте), указывающий на `.m-verify-worktrees/{session_id}` вместо реального `TEST WORKFLOW/`. Это требует, чтобы промпты слоёв A–J не зашивали абсолютный путь `TEST WORKFLOW/` жёстко — интеграционное требование к A–J, см. §12.

### 4.3 Восстановление после сбоя M-сессии (R3, закрывает S-5)

M-сессия — многошаговый процесс (M1 вызывает M2–M8 последовательно), который может прерваться (закрытие терминала, сбой subagent, обрыв соединения) на любом шаге. Без явного состояния сессии человек не может безопасно возобновить работу — непонятно, что уже сделано, а что нет.

```
m_session_state.yaml (sessions/{session_id}/, обновляется на КАЖДОМ переходе
                       конечного автомата §5, а не только в конце)
  session_id
  current_state: diagnosing | architecting | specifying | test_writing |
                 engineering | qa_review | documenting | done | escalated
  trigger_ref: MTS-{seq}
  produced_artifact_refs: [MAR-001, MPS-001, ...]   # уже произведённые на этот момент
  meta_fix_attempt_count
  updated_at
  terminal: bool                                     # true при done|escalated
```

Preflight M1 (§4.1, п.3): при старте M1 сканирует `.m-worktrees/*`, `.m-verify-worktrees/*` и ветки `m/*` на предмет `m_session_state.yaml` без `terminal: true`. При находке — предлагает человеку:
- **resume** — продолжить с `current_state`, используя уже произведённые артефакты (`produced_artifact_refs`) как вход следующего шага;
- **abort с очисткой** — `git worktree remove`, удаление ветки `m/*`, `m_session_state.yaml` помечается `terminal: true` задним числом с `outcome: aborted_by_human`. Checkpoint §6.2 (если был создан) не трогается — он в основной ветке, не в worktree.

**Конкурентные сессии (R3, закрывает Minor 4):** если найден второй `m_session_state.yaml` без `terminal: true`, отличный от той сессии, что человек сейчас пытается запустить/возобновить — M1 останавливается и спрашивает человека явно, т.к. `meta_session_log.yaml` (§9) спроектирован в предположении одной активной M-сессии одновременно.

## 5. Протокол исправления (`reactive_fix`) — Step 0–4 как конечный автомат

Формализация алгоритма из ТЗ, реструктурированная в R3 под TDD. Состояния: `diagnosing → (architecting) → specifying → test_writing → engineering → qa_review → documenting → done | escalated`. `verifying` как отдельное состояние после вердикта — упразднено (R3): прогон тестов стал частью входа в `qa_review` (§5.8), а не действием после approve.

### 5.1 Diagnosing (M2 Meta-Analyst)

```
Вход: meta_trigger_signal.yaml (reactive_pattern, source_layer, source_agent_id,
      evidence refs — ссылки на конкретные артефакты/логи), либо prerequisite_ref
      (для prerequisite_check, §2.4)

M2 читает:
  - промпт(ы) вовлечённых агентов
  - фактические артефакты обмена (напр. hX_revision_request.yaml и ответ на него)
  - Architecture Plan слоя (контракт, который агенты должны были соблюдать)
  - known_limitations.yaml (§9.14, R3) — если инцидент совпадает с уже принятым
    ограничением, M2 поднимает существующую запись человеку вместо диагностики с нуля

M2 классифицирует root_cause_class:
  transient_execution_error   — промпт корректен, агент один раз ошибся →
                                 НЕ требует правки промпта; просто перезапуск
                                 агента слоя (вне M-слоя). M-сессия завершается
                                 здесь с outcome: no_action_needed.
  prompt_defect                — промпт одного агента сформулирован плохо
                                 (двусмысленность, отсутствующая секция,
                                 нет explicit output schema)
  protocol_mismatch            — два промпта не согласованы друг с другом
                                 (разные названия полей, разные допущения
                                 о формате возврата) — требует правки
                                 в ≥2 промптах согласованно
  optimization_opportunity      — (для retrospective/audit only) не дефект,
                                 но есть более эффективный путь
  false_positive                — (R3, для prerequisite_check / random_audit)
                                 заявленный паттерн/находка при ближайшем
                                 рассмотрении не воспроизводится и не является
                                 дефектом — сессия завершается без правки,
                                 исход зависит от режима (§2.4, §9.2)

requires_architecture_change (bool): true, если решение затрагивает >1 промпт,
  порядок агентов, или сам Architecture Plan слоя (напр. protocol_mismatch почти
  всегда → true; изолированный prompt_defect в одном промпте → обычно false)

Примечание: `reactive_pattern: schema_mismatch_detected` (§2.2) почти всегда
классифицируется M2 как `root_cause_class: protocol_mismatch` — рассинхрон
схем producer/consumer по определению затрагивает ≥2 промпта — и, соответственно,
почти всегда `requires_architecture_change: true`.

Выход: m_analysis_report.yaml
```

Если `root_cause_class: transient_execution_error` или `false_positive` → M1 завершает сессию (`outcome: no_action_needed`), без входа в M3–M8.

### 5.2 Определение `loop_exceeds_threshold` (детектор для M2, неинвазивный)

Вместо требования, чтобы все слои A–J завели единое поле "revision_cycle_count" (инвазивная правка всех существующих промптов), M2 считает цикл **по факту наличия артефактов** в папке слоя:

```
count = число артефактов вида "{agent}_revision_request*.yaml" (или его аналог
        в конкретном слое — h*_revision_request.yaml, g*_revision_report.yaml
        с recurring find/fix между теми же двумя agent_id) между ОДНОЙ И ТОЙ ЖЕ
        парой (maker_agent_id, checker_agent_id) по ОДНОМУ И ТОМУ ЖЕ target
        artifact_id за время текущего прогона слоя (не за всю историю проекта)

if count > 3: reactive_pattern = loop_exceeds_threshold (подтверждено)
```

Это позволяет M-слою работать без правок в H/G/J-слоях сегодня же — считает по существующим файлам. Если в будущем слои явно материализуют `revision_cycle_count` в своих run-артефактах, M2 предпочитает явное поле (дешевле, надёжнее), но не требует этого как предусловие.

**Граница «текущего прогона слоя» (R3, дополняет W-3):** `count` считается только по артефактам, относящимся к **текущему** прогону слоя, не ко всей истории проекта. M2 отсекает более старые артефакты одним из способов (по убыванию предпочтения):
1. по `run_id`/`session_id` полю в самих артефактах, если слой его материализует;
2. по таймстампам файлов относительно момента старта текущего прогона слоя (человек указывает эту точку отсчёта M1 на старте, если она не следует однозначно из git-истории);
3. по диапазону коммитов `TEST WORKFLOW/.git` между началом текущего прогона и `HEAD`.

Это эвристика, а не точный протокол — если ни один из трёх способов не даёт уверенного ответа, M2 честно фиксирует это как ограничение анализа в `m_analysis_report.yaml.evidence_summary`, вместо того чтобы притворяться точностью, которой нет (тот же принцип, что и в P2, §0).

### 5.3 Architecting (M3 Meta-Architect) — только если `requires_architecture_change: true`

```
Вход: m_analysis_report.yaml (root_cause_class: protocol_mismatch, как правило)

M3 проектирует решение на уровне архитектуры слоя:
  - какие промпты меняются согласованно
  - меняется ли схема хендоффа между ними
  - нужен ли новый агент / нужно ли исключить агента
  - формулирует revision entry для "{Layer} Architecture Plan.md" в СТИЛЕ,
    уже принятом в проекте (см. J-план R1..R13: пронумерованная ревизия,
    один абзац с summary изменений, ссылки на секции)

Выход: m_architecture_change_proposal.yaml (§9.3)
```

Если `requires_architecture_change: false`, шаг пропускается — M1 передаёт `m_analysis_report.yaml` напрямую в M4.

### 5.4 Specifying (M4 Meta-Methodologist)

```
Вход: m_analysis_report.yaml (+ m_architecture_change_proposal.yaml, если есть)

M4 переводит диагноз в конкретные, проверяемые требования к правке промпта(ов),
обосновывая КАЖДОЕ требование ссылкой на известный принцип поведения LLM
(не "стилистическое предпочтение", а конкретная причина):

Примеры категорий обоснования (`llm_behavior_principle`):
  - ambiguous_instruction      — инструкция допускает ≥2 несовместимых прочтения
  - missing_output_schema       — агент не видел явной структуры ожидаемого
                                  вывода → структурный дрейф формата
  - contradictory_constraints   — секция A требует X, секция B (неявно) требует not-X
  - implicit_precondition       — промпт предполагает контекст, который агенту
                                  не передан явно (сирота-допущение)
  - order_sensitivity           — порядок шагов в промпте противоречит порядку,
                                  в котором агент реально должен принимать решения
  - missing_revision_handling   — нет секции "как обработать revision_request от
                                  downstream" (см. Maker-Checker convention,
                                  уже принятую в H-слое, §8)
  - overloaded_role             — один промпт совмещает несовместимые роли,
                                  из-за чего агент противоречит сам себе между
                                  прогонами

Выход: m_prompt_change_spec.yaml — по одному блоку required_edits на промпт
(вход для M5 Test Writer, §5.5, и позже M6 Engineer, §5.7)
```

### 5.5 Test Writing (M5, новый агент, R3)

```
Вход: m_prompt_change_spec.yaml (M4) + m_analysis_report.yaml (evidence оригинального
      дефекта)

M5 пишет тесты для КАЖДОГО required_edit из m_prompt_change_spec.yaml, по таксономии
Tier 0/1/2 (§5.6), плюс минимум один regression-тест, воспроизводящий именно тот
дефект, что зафиксирован в evidence (m_analysis_report.evidence_summary /
loop_evidence / schema_mismatch_evidence).

**Обязательная красная фаза:** написанные тесты прогоняются против ТЕКУЩЕГО
(багованного, ещё не исправленного) текста промпта. Ожидаемый результат — FAIL
(тесты обязаны воспроизвести дефект). Если тесты проходят на багованном промпте
("зелёная фаза" на старте) — значит:
  - тест написан неверно (не проверяет то, что нужно) → M5 переписывает тест, ИЛИ
  - диагноз/spec неверны (дефекта, который описал M2/M4, на самом деле нет в том
    виде, как его сформулировали) → возврат к M4 (spec неверен) или к M2
    (диагноз неверен), ДО того как M6 (Engineer) потратил HITL-итерации на
    правку несуществующей или неверно описанной проблемы.

Это ключевая экономия R3: без red-фазы возможна ситуация, где Engineer правит
промпт по неверному spec, а Checker потом просто подтверждает, что новый текст
проходит тест — который с самого начала был бесполезен, потому что проходил
и на старом, багованном тексте тоже.

Выход: m_test_spec.yaml (§9.5) + файлы тестов в ветке m/{session_id}/{slug}
       (корневой репозиторий, расположение — §6.1)
```

### 5.6 Таксономия тестов (R3)

Три уровня, от дешёвого/детерминированного к дорогому/вероятностному:

```
Tier 0 — структурные
  Детерминированные ассерты на текст промпта: нужная секция существует, блок
  output schema присутствует и парсится (если формат YAML/JSON-подобный),
  enum-словари в тексте совпадают с ожидаемыми, нет ссылок на устаревшие
  артефакты/поля. Исполнитель — скрипт (prompt_test_runner.py или аналог),
  НЕ LLM-прогон. Дёшево, быстро, всегда включено.

Tier 1 — контрактные
  Сверка схемы выхода producer-промпта со схемой входа consumer-промпта:
  имена полей, типы, enum-словари совпадают между двумя промптами одного
  хендоффа. Тоже скрипт, не LLM. Это тот же механизм, что предлагается
  вынести в standing preflight слоёв A–J как контрактный линтер (§12) —
  Tier 1 в тестовом корпусе M-слоя и линтер оркестратора слоя — одна и та
  же проверка, применяемая в двух разных точках жизненного цикла.

Tier 2 — поведенческие
  Golden input → прогон агента как subagent в verify-worktree (§6.3) →
  ассерты на СВОЙСТВА произведённого артефакта (схемно валиден, нужное поле
  присутствует, значение соответствует ожидаемому enum, исходный дефект из
  evidence отсутствует). НИКОГДА exact-match полного текста вывода — LLM
  недетерминирован, точное совпадение — гарантированно хрупкий тест.
  Для спорных случаев (§2.3, системный vs разовый дефект) — n прогонов
  с порогом k/n (§5.6.1).
```

#### 5.6.1 Экономика прогона Tier 2 (R3)

Полный n-прогонный Tier 2 на каждый фикс — дорого (каждый прогон — subagent-сессия). Правило по умолчанию:

```
Tier 0 / Tier 1  — всегда, на весь корпус промпта (дёшево, детерминированно)
Tier 2           — один golden-прогон при каждом фиксе (достаточно для
                   большинства prompt_defect правок)
Tier 2, n-прогон — только когда:
                   (a) requires_architecture_change: true (M3 участвовал,
                       ставки выше — protocol_mismatch затрагивает ≥2 промпта), ИЛИ
                   (b) есть спор о системности дефекта (§2.3) — n/k тест
                       используется как эмпирическое разрешение спора
```

Стоимость прогона (число вызовов subagent, оценка токенов) логируется в `m_test_run_report.yaml` (§9.9) — это позволяет пересмотреть правило по умолчанию на основе фактических данных, а не догадки.

#### 5.6.2 Деградация для HITL-агентов (R3, закрывает S-2a)

Не все агенты пайплайна rerun-able одинаково. Часть агентов слоёв A–J — сами HITL-сессии с человеком в цикле (G7, I22, J11 и аналогичные — см. память проекта по I/J-слоям). Их вход включает решения человека, принятые интерактивно, которые Tier 2 не может воспроизвести детерминированно (нет «того же» golden input в строгом смысле — часть входа была диалогом).

```
Для HITL-целевых агентов:
  Tier 0 / Tier 1 — доступны полностью, без изменений
  Tier 2          — НЕДОСТУПЕН в полном виде. Потолок:
                    - если промпт агента делится на автоматизируемый под-шаг
                      (часть логики не требует решения человека) — поведенческий
                      тест пишется на этот под-шаг изолированно
                    - если не делится — Tier 2 для этого агента отсутствует,
                      это ЯВНО фиксируется в m_test_spec.yaml
                      (tier_2_available: false, причина) как честное
                      ограничение, а не замалчивается
```

Это ограничение реальное, не временное — HITL-сессии по определению не детерминированы в части, зависящей от человека. План фиксирует его открыто, вместо того чтобы предполагать полное покрытие, которого не может быть.

### 5.7 Engineering + HITL (M6, Maker)

```
Вход: m_prompt_change_spec.yaml, m_test_spec.yaml (тесты уже написаны и
      подтверждены в красной фазе, §5.5 — M6 правит промпт, ЗНАЯ, какой
      тест должен стать зелёным)

M6 предлагает конкретный diff промпт-файла(ов) человеку. Формат сессии — как
G4/G7 co-authoring и J21 HITL Coder Session: агент приносит суждение (может
не согласиться с формулировкой требования из M4 и явно сказать почему), но
финальное решение — за человеком. Итеративно, до explicit accept человека.

Committer: M6 коммитит принятый diff в m/{session_id}/{slug} (корневой репо,
та же ветка, где уже лежат тесты M5).

Выход: m_engineer_session.yaml (diff_summary, iterations, final_commit_hash)
```

**Правило отката при rejected (M7):** если M7 (§5.8) отклоняет изменение — не откатываемся сразу к Step 1 вслепую. Сначала M1 спрашивает: ошибка в ТРЕБОВАНИЯХ (M4 неверно сформулировал spec), в ТЕСТАХ (M5 написал тест неверно — проверяет не то, или сам тест некорректен) или в РЕАЛИЗАЦИИ (M6 отступил от верного spec)? Обычно это видно из `m_qa_report.yaml.reason_if_rejected` и из `test_run_report_ref` (§9.9) — какой конкретно тест не прошёл и почему.
- Реализация не соответствует spec/тестам → назад к M6 (тот же spec, новая попытка)
- Тест сам был неверным (ложно-красный/ложно-зелёный) → назад к M5 (переписать тест)
- Spec сам был неверным/неполным → назад к M4 (пересмотр требований)
- Диагноз сам оказался неверным (дефект глубже, чем думали) → назад к M2

Это уточнение самого протокола ТЗ: "если не ок → откатываемся на шаг 1" буквально означало бы всегда возврат к M6, но на практике причина отказа может лежать выше по цепочке — слепой возврат к Step 1 тратит итерации впустую и рискует упереться в тот же порочный цикл, который M-слой призван устранять (см. §5.9, guard против собственного зацикливания). При возврате M1 пишет `m_engineer_revision_request.yaml` (§9.7) — тот же паттерн, что Maker-Checker конвенция в H-слое (§8).

### 5.8 QA + Test Runner (M7, Checker)

```
Вход: m_engineer_session.yaml (финальный diff), m_prompt_change_spec.yaml,
      m_test_spec.yaml (M5), исходный m_analysis_report.yaml (evidence
      оригинальной проблемы)

M7 выполняет ДВЕ роли за один вердикт (R3, было разделено на QA + отдельный
шаг "verifying" — упразднено, см. revision note):

  1. Compliance review — соответствует ли diff требованиям M4 (по каждому
     required_edit), не противоречит ли (a) соседним промптам этого же слоя
     по одному хендоффу (immediate neighbor contract check), (b) инвариантам
     Architecture Plan слоя.

  2. Прогон тестового корпуса (§6.3 — механика изолированного прогона):
     - Tier 0 / Tier 1 — всегда, весь корпус промпта
     - Tier 2 — golden-прогон обязателен; n/k-прогон — по правилу §5.6.1
     - Ключевая проверка: red→green — тест(ы), которые M5 подтвердил как
       красные на старом промпте (§5.5), теперь обязаны быть зелёными на
       новом. Тест, красный и до, и после — фикс не сработал. Тест, зелёный
       и до, и после — тест бесполезен (не проверяет исправляемое).

Вердикт approved требует ОБА пункта: compliance И test_run_report
(red_green_matrix_ok: true, §9.9). Провал любого из двух — rejected.

Выход: m_qa_report.yaml, verdict: approved | rejected
       (test_run_report_ref → m_test_run_report.yaml, §9.9)
```

Провал тестов при вердикте `rejected` **инкрементирует** `meta_fix_attempt_count` (§5.9) наравне с провалом compliance-проверки — оба исхода одинаково расходуют попытку, т.к. оба требуют новой итерации M6 (или выше по цепочке, §5.7).

### 5.9 Guard против бесконечного цикла внутри самого M-слоя

Ирония, которую нельзя игнорировать: M-слой существует, чтобы ловить `loop_exceeds_threshold` между двумя агентами — но цикл M6↔M7 (Maker↔Checker) структурно устроен точно так же и подвержен той же болезни.

```
meta_fix_attempt_count: инкрементируется при каждом возврате M7→M6 (или M7→M5,

                         (§5.8), не только compliance

    M-сессию (запрет на самозапуск M-слоя внутри M-слоя). Пишет m_escalation.yaml
```

### 6.1 Разделение ответственности

```
Корневой репозиторий (c:\Projects\software_workflow\.git)
```

### 6.3 Изолированная верификация (Step 2 из ТЗ)

Это самый деликатный узел протокола: нужно прогнать тестовый корпус (§5.6, включая исправленный промпт) против **тех же входных данных**, что вызвали баг — не трогая при этом реальный прогресс слоя, который мог уйти вперёд (слой мог быть уже на шаге G9, когда чинится G4).

```
1. Найти во вложенном репозитории (TEST WORKFLOW\.git) коммит(ы), отражающие
   состояние ДО запуска проблемного промпта:
   - commit_level (P2): найден отдельный коммит "Run {agent_id} ..." →
     точка отсчёта = commit~1 (родитель)
   - manual_diff_level (P2): коммит смешанный → человек указывает вручную,
     какие файлы отражают "вход" агента; M1 фиксирует это явно в
     m_test_run_report.yaml (§9.9) как manual_precision_note (честно, не
     притворяется точностью, которой нет)

2. M1 создаёт verify-worktree:
   git -C "TEST WORKFLOW" worktree add .m-verify-worktrees/{session_id} <hash>

3. M1 копирует исправленный промпт-файл (из m/{session_id}/{slug}, корневой
   репо) во временное расположение, видимое запускаемому subagent

3a. M1 передаёт запускаемому subagent явный параметр корня артефактов,
    указывающий на .m-verify-worktrees/{session_id} (не на реальный
    TEST WORKFLOW/) — см. §4.2. Без этого subagent рискует писать/читать
    из реального прогресса слоя, который мог уйти вперёд (R3, закрывает S-2b)

4. M1 запускает агента слоя (тот же, что раньше произвёл баг) как subagent
   через Agent tool, с ИСПРАВЛЕННЫМ промптом, против golden input (Tier 2
   асерты из behavioral/{case_id}, §5.6) — либо против исходного триггерного
   входа, если тест ещё не существовал раньше самого инцидента

5. Сравнение: устранена ли исходная проблема (evidence из m_analysis_report)?
   Прогнать также immediate neighbor(ы) — ближайший агент выше/ниже по
   хендоффу — на предмет регресса контракта (не обязательно весь слой целиком;
   полный прогон слоя — по решению M1/человека, только если M3 участвовал,
   т.к. затронута архитектура нескольких промптов, см. §6.3.1)

6. Результат → m_test_run_report.yaml (§9.9), на который m_qa_report.yaml
   (§9.8) ссылается через test_run_report_ref (M7 читает результат
   верификации, это часть compliance-проверки, не отдельный шаг вне M7)

7. Verify-worktree НЕ мержится и не коммитится в основную ветку
   TEST WORKFLOW — это одноразовая проверочная среда. Удаляется после review
   (git worktree remove), если только человек не просит сохранить для аудита.
```

**6.3.1 Масштаб регрессии (осознанное решение об экономии):** запуск ВСЕГО слоя целиком ради проверки одной точечной правки промпта — дорого и часто избыточно. Обязательный минимум: (a) прямой повтор именно того агента, что чинили, против триггерного входа; (b) contract-check с непосредственными соседями по хендоффу (один агент вверх, один вниз). Полный прогон слоя — опционален и рекомендуется только когда `requires_architecture_change: true` (т.е. M3 участвовал и переписал контракт, затрагивающий больше одного стыка). См. также экономику Tier 2 в целом — §5.6.1.

**6.3.2 HITL-агенты:** см. §5.6.2 — для целевых агентов без возможности детерминированного Tier 2 применяется описанный там потолок покрытия; verify-worktree в этом случае используется только для автоматизируемого под-шага, если он существует.

### 6.4 Слияние в основную ветку и распространение в реальный прогон слоя

После approve M7 и успешной верификации (§6.3):

```
0. Тестовый корпус (M5, §5.5) уже закоммичен в ту же ветку — отдельного
   шага для тестов не требуется (R3, §6.1)
1. M1 мержит m/{session_id}/{slug} → main (корневой репозиторий), ТОЛЬКО
   после явного "да" от человека (не автоматически — это редактирование
   процесса пайплайна, а не рутинная задача)
2. Если реальный прогон слоя УЖЕ ушёл дальше проблемного агента и уже
   произвёл вниз по цепочке артефакты, зависевшие от бага:
   M1 НЕ запускает пересчёт сам. M1 пишет явное уведомление человеку/
   layer-оркестратору: "промпт {agent_id} исправлен; артефакты
   {artifact_ids}, произведённые до исправления, могли унаследовать баг;
   решение о пересчёте — за слоем, через его штатный upstream_resync/
   revision_request механизм (см. §7)"
3. Мета-слой не решает сам, стоит ли пересчитывать — это решение по
   стоимости/риску принимает владелец слоя (человек), т.к. пересчёт может
   быть дорогим (напр. целая HITL сессия G7 заново)
```

## 7. Распространение исправления через существующий resync-протокол слоя

Ключевой принцип этого плана (см. Факт 3, §0): **M-слой не изобретает собственный каскадный механизм пересчёта нижестоящих артефактов.** Каждый слой уже умеет обрабатывать «апстрим изменился после того, как я уже закончил» — это `revision_kind: upstream_resync` в G/H-слоях и `hX_revision_request.yaml` протокол. Если пересчёт нужен (решение человека, §6.4), он выполняется штатным способом ЭТОГО слоя, тем же путём, каким слой уже обрабатывает любое другое позднее изменение апстрима — M-слой лишь поставляет исправленный промпт и явное уведомление, что стоит пересчитать.

Это сознательно исключает необходимость проектировать отдельный "meta cascade protocol" — экономия сложности, соответствующая правилу не добавлять абстракции сверх необходимого.

## 10. Random audit (`random_audit`)

```
0. (R3) Перед чтением текста промпта M2 прогоняет его СУЩЕСТВУЮЩИЙ тестовый
   корпус, если он есть ({Layer}/tests/{agent_id}/, §6.1): Tier 0/1 — всегда;
   Tier 2 — по наличию golden inputs. Результат (test_suite_zero_step_ref,
   §9.2) включается в m_analysis_report.yaml как часть evidence — находка о
   провале существующего теста эквивалентна находке, обнаруженной человеком.
1. M1 строит реестр всех промпт-файлов на лету:
   glob "*/[A-M][0-9]*. *.md" по корню репозитория (папки A. Idea Note Layer …
   M. Meta Layer включительно — M-слой сам подлежит будущему аудиту, §5.9)
2. M1 читает meta_audit_history.yaml
3. Выбор: взвешенно-случайно, приоритет — никогда не аудированные промпты,
   затем давно не аудированные (по last_audited_at)
4. M2 (audit mode), после шага 0, читает: сам промпт, релевантную секцию
   Architecture Plan слоя, и — если существуют — последние произведённые
   этим агентом артефакты (выборка, не всё) как эмпирическую проверку
   "делает ли агент то, что промпт заявляет"
5. M2 оценивает по методологическому чек-листу (те же категории, что в §5.4:
   ambiguous_instruction, missing_output_schema, contradictory_constraints,
   implicit_precondition, order_sensitivity, missing_revision_handling,
   overloaded_role) — produces m_analysis_report.yaml, root_cause_class
   обычно optimization_opportunity, prompt_defect или false_positive (advisory
   severity)
6. Severity: advisory (по умолчанию, ничего не блокирует) | blocking
   (реальный дефект найден случайно — конвертируется в обычный reactive_fix
   путь, §5, minus M2 diagnosing, т.к. уже сделан)
7. M1 обновляет meta_audit_history.yaml независимо от исхода
```

### 10a. Побочная функция корпуса: канарейка смены модели (R3)

Тестовый корпус (§6.1) решает не только задачу «проверить фикс», но и задачу, которую план изначально не проектировал под неё: обнаружение регрессий промптов при обновлении underlying-модели Claude. Это пятый сценарий запуска, отдельный от четырёх `trigger_mode` (§2.1, §2.4) — оформлен как `trigger_mode: random_audit` в batch-режиме (весь реестр разом, а не одна случайная выборка):

```
1. При обновлении версии модели — прогон Tier 0/1 по ВСЕМ промптам реестра
   (дёшево, детерминированно) + Tier 2 по всем имеющимся golden inputs
2. model_version (§9.1, §9.9) фиксируется в каждом отчёте о прогоне
3. Результат — model_migration_checks (§9.13, meta_audit_history.yaml)
4. Регрессия (тест, ранее зелёный, стал красным на новой модели без правки
   промпта) → заводится обычный reactive_fix (root_cause_class остаётся
   prompt_defect — промпт, рассчитанный на поведение старой модели, стал
   двусмысленным для новой)
```

Частота запуска (по расписанию / вручную при объявлении новой модели) — открытый вопрос, см. OQ-M-007, симметрично общей неспроектированности частоты `random_audit` (OQ-M-004).

## 12. Интеграционный контракт с другими слоями (требуется от A–J, не самим M-слоем)

Минимальный список изменений, которые НЕ входят в объём M-слоя, но нужны слоям A–J, чтобы контракт §9.10 (было §9.7) работал:

1. Оркестратор/человек каждого слоя перед запуском конкретного агента проверяет `TEST WORKFLOW/M. Meta Layer RS/prerequisites/{agent_id}/*.yaml` (R3 — путь с поддиректорией, §9.10) на наличие хотя бы одной записи со `status: pending` (аналогично preflight-проверкам, уже принятым в J0 §3.3)

2. Коммиты в `TEST WORKFLOW/.git` (и, после P1, в корневом репозитории) желательно делать зернисто — один коммит на один запуск агента, с единообразным сообщением `[{layer}{agent_id}] {краткое summary}` (по аналогии с J-слоем `[{task_id}] {step_name}:`). Это не блокирует M-слой сегодня (см. manual_diff_level, §0/P2), но повышает точность будущих откатов.

3. **(R3) Материализация `schema_mismatch_detected` через `inbox/`.** Когда оркестратор слоя сам замечает несоответствие схемы хендоффа (§2.2), он не пытается сам решить проблему — он пишет черновик `meta_trigger_signal.yaml` (detected_by: layer_orchestrator, materialized_by_orchestrator: true, §9.1) в `TEST WORKFLOW/M. Meta Layer RS/inbox/` и останавливает хендофф с уведомлением человеку. Это требует явного права записи в `inbox/` для оркестраторов слоёв A–J (новая директория, право записи разрешено только туда, не в остальную структуру M-слоя). Человек стартует M1; M1 в preflight (§4.1, п.1) читает `inbox/` наравне с интерактивным интервью — это сохраняет Инвариант 3 (запуск всё равно человеко-инициирован, просто форма сигнала уже готова).

4. **(R3) Контрактный линтер как standing preflight.** Tier 1 (§5.6) — не только часть тестового корпуса M-слоя, но самостоятельный инструмент, который оркестратор КАЖДОГО слоя запускает перед хендоффом между двумя своими агентами (сверка схемы выхода N со схемой входа N+1). Это переводит `schema_mismatch_detected` из случайной находки человека/агента в систематическую, автоматическую проверку — при внедрённом линтере пункт 3 выше вырождается в «линтер упал, см. лог» вместо «оркестратор заметил на глаз». Частота запуска линтера (CI/pre-commit корневого репозитория vs вручную оркестратором) — открытый вопрос, см. OQ-M-007.

5. **(R3) Параметризация корня артефактов.** Промпты слоёв A–J не должны жёстко зашивать абсолютный путь `TEST WORKFLOW/` — обязаны принимать переопределение корня (env-переменная или явная подстановка в промпте при запуске subagent), иначе verify-worktree (§6.3, §4.2) и Tier 2 тесты (§5.6) не могут безопасно прогонять агента изолированно от реального прогресса слоя.

Это открытые пункты, не блокирующие DRAFT-статус этого плана — фиксируются как зависимости в §15.

## 13. Инварианты

1. M-слой не редактирует сгенерированные данные-артефакты в `TEST WORKFLOW/*`, только промпты, Architecture Plan-документы и собственный тестовый корпус.
2. M-слой не редактирует код продукта (вывод J-слоя) и служебные БД (`pipeline.db`, `causal_graph.db`, `tasks.db`).
3. M-слой всегда человеко-инициирован; нет фонового/автоматического триггера.
4. Merge исправленного промпта в основную ветку — только по явному подтверждению человека (§6.4), никогда автоматически.
5. Verify-worktree (§6.3) никогда не мержится в основную ветку артефактного репозитория.
6. `transient_execution_error` и `false_positive` завершают сессию без входа в M3–M8 (нет правки промпта без диагностированной системной причины).
7. `qa_found_prompt_attributable_defect` фиксируется только при системной (не разовой) природе дефекта — фильтр шума §2.3.
8. Guard `meta_fix_max_attempts` (§5.9): M-слой никогда не порождает рекурсивный `meta_trigger_signal` на собственную текущую сессию.
9. Пересчёт нижестоящих артефактов после исправления промпта выполняется штатным resync-протоколом слоя (§7), не собственным механизмом M-слоя.
10. Step 4 (поиск аналогичной проблемы в других промптах) не редактирует найденные промпты немедленно — только помечает `meta_layer_prerequisite.yaml` (§9.10); правка ждёт реального следующего запуска этого промпта.
11. **(R3)** Любая правка промпт-файла выполняется только через M-сессию и сопровождается обновлением его тестового корпуса (§5.5, §6.1); правка в обход M-слоя, без соответствующих тестов — нарушение процесса.
12. **(R3)** Красная фаза обязательна: правка промпта (M6, §5.7) не начинается, пока написанный тест не воспроизвёл дефект на старом тексте промпта (§5.5) — за исключением `prerequisite_check` (§2.4, гипотеза, не подтверждённый дефект) и находок `optimization_opportunity` (§5.1, дефекта нет по определению).

## 14. Предложения и улучшения сверх исходного ТЗ (явно выделены для решения)

Ниже — места, где план не просто формализует переданный алгоритм, а осознанно расширяет или уточняет его. Каждое — решение, которое стоит либо принять, либо явно отклонить:

1. **Разделение на 7 агентов вместо 6** (R1) — в ТЗ была задвоенная нумерация ("6. Мета-QA" и "6. Мета-документер"). Принято как M1–M7 (Documenter = M7). См. п.10 ниже — R3 расширяет ростер до 8.
2. **Фильтр шума для триггера 3** (§2.3) — без него M-слой запускался бы на каждый штатный QA `failed`, что и так случается регулярно в текущем пайплайне.
3. **Неинвазивный детектор `loop_exceeds_threshold`** (§5.2) — считает по существующим артефактам, не требует немедленной правки схем всех слоёв.
4. **Уточнение "куда откатываемся, если QA отклонил"** (§5.7) — исходное "откат на шаг 1" заменено на маршрутизацию по фактической причине отказа (M6/M5/M4/M2), чтобы не тратить попытки впустую и не подставляться под тот же порочный цикл, который M-слой должен ловить.
5. **Guard против зацикливания самого M-слоя** (§5.9) — симметрия с проблемой, которую слой призван решать, требует явного предохранителя.
6. **Переиспользование `upstream_resync`-протокола слоёв** (§7) вместо отдельного каскадного механизма — прямая экономия сложности.
7. **M-слой не решает сам, пересчитывать ли нижестоящие артефакты** (§6.4) — решение всегда за человеком/владельцем слоя, т.к. может быть дорогим.
8. **Честная деградация точности отката** (`commit_level` / `manual_diff_level`, P2) — вместо того, чтобы притворяться точностью отката, которой сегодняшняя гранулярность коммитов не даёт.
9. **Явное предусловие P1** (пустой корневой `.git`) — без этого часть механики (checkpoint/rollback промпт-файлов) не работает; зафиксировано как открытая зависимость, а не тихое допущение.
10. **(R3) Реструктуризация FSM под TDD и расширение ростера с 7 до 8 агентов** (§5, §8) — `test_writing` (новый M5) вставлен перед `engineering`, `verifying` как отдельное пост-вердиктное состояние упразднено. Решение: тест должен существовать и быть красным ДО того, как Engineer тратит HITL-итерации на правку — иначе Checker рискует одобрить фикс, для которого не было независимого критерия успеха, кроме повторного суждения того же типа агента.
11. **(R3) Контрактный линтер как standing preflight слоёв A–J** (§12) — вместо того чтобы Tier 1 (§5.6) жил только внутри тестового корпуса M-слоя (реактивно, после инцидента), тот же механизм предлагается как проактивная проверка перед каждым хендоффом. Компромисс: требует внедрения в промпты/процесс A–J, вне прямого контроля M-плана — зафиксировано как открытая интеграционная зависимость (§12), не как готовое решение.
12. **(R3) Канарейка смены модели** (§10a) — тестовый корпус, изначально спроектированный только для проверки фиксов, даёт побочную способность детектировать регрессии от обновления модели. Решение: оформить как batch-вариант `random_audit`, а не отдельный `trigger_mode` — экономия сложности (симметрично §7 про resync-протокол).
