## Классификация проблем

| Класс | Определение | Действие |
|---|---|---|
| `spec_defect` | Проблема в самой спецификации H3: ошибка, пропуск, нарушение правил | Return to H3 |
| `upstream_architecture_blocker` | Проблема коренится в upstream gap (из H1/H2) которую H3 не мог разрешить | Proceed с флагом; downstream impact документируется |

### Смешение классов запрещено

Если H3 применил documented gap_assumption для H2-зафиксированного gap → это не spec_defect. Spec_defect только если H3 игнорировал gap без assumption, или применил assumption некорректно.

### H2 module-layer blocker rule

Если в `h2_traceability_qa_report.yaml` присутствует `upstream_traceability_blocker` с `blocking_for_layer: module`:

1. H4 **сначала** проверяет, корректно ли H3 отразил blocker — через `speculative: true`, `provisional_only: true`, `gap_assumptions`, `open_questions`, или `ready_for_h4: false`.
2. Корректное отражение → производная неполнота = `upstream_architecture_blocker`, не spec_defect.
3. Игнорирование blocker → `spec_defect (significant)`.
4. Некорректный механизм (например, `stable` вместо `speculative`) → `spec_defect (significant)`.

### Return threshold rule

`proceed: false` если:
- есть хотя бы один spec_defect с severity `blocking`
- ИЛИ есть хотя бы один spec_defect с severity `significant`
- ИЛИ есть unowned approved surfaces (любое количество)

`proceed: true` если: нет blocking spec_defects, нет significant spec_defects, нет unowned surfaces.
Upstream_architecture_blockers **не влияют на proceed** — они влияют только на статус.

Промежуточного состояния нет: любой `significant` defect → `failed`, не `passed_with_flags`.

**Статус при proceed: true:**
- `passed` — zero spec_defects (всех severity) И zero UAB
- `passed_with_flags` — есть informational spec_defects И/ИЛИ UAB (нет significant/blocking)

## Правило интерпретации provisional/speculative

H4 **не штрафует** provisional decisions.

H4 проверяет:
1. Что provisional decisions **явно маркированы** (не скрыты как stable)
2. Что speculative modules имеют documented `gap_assumptions`
3. Что `open_questions` с urgency `blocks_h4_review` (или `must_resolve_before_h4`) действительно resolved — escalation downstream не является resolution
4. Что эскалированные open_questions направлены корректному агенту

Unmarked provisional decision → spec_defect (significant).
Speculative module без gap_assumptions → spec_defect (blocking).

### Open question routing rule

| Тип вопроса | Ожидаемый routing | Ожидаемая маркировка связанного решения/поля |
|---|---|---|
| state/type/Model ownership | H5 | `requires_h5_confirmation` |
| effects, ports, Cmd/Sub, persistence | H7 | `requires_h7_confirmation` |
| view decomposition, component boundaries | H10 | `requires_h10_confirmation` |
| host integration, external package, cross-layer | H12 | `requires_h12_confirmation` |
| вопрос, блокирующий H4 review | upstream или HITL | confidence не требуется на самом `open_question` |

`open_questions[]` в H3 не содержит собственного поля `confidence`; H4 проверяет confidence/sentinel у связанного решения или поля, если такая связь явно присутствует. Нельзя требовать `confidence` непосредственно на `open_question`.

Для `urgency: blocks_h4_review` (и legacy alias `must_resolve_before_h4`) routing должен быть `upstream` или `HITL`, не H5/H7/H10/H12. Нарушение этого правила → spec_defect (significant), потому что H3 сам признал вопрос блокирующим до H4.

Routing mismatch для обычных downstream-вопросов → spec_defect (informational). Для `blocks_h4_review` применяется significant rule выше.

**blocks_h4_review rule:** `blocks_h4_review` (или `must_resolve_before_h4`) — это H3's own label, означающий что H3 сам признал вопрос нерешённым до H4. Если такой вопрос `status: open` или `status: escalated` (не resolved) — H4 фиксирует spec_defect (significant) с рекомендацией: "H3 должен либо resolve этот вопрос, либо понизить urgency если H4 может работать без него." Escalation к H12 или другому агенту не является resolution — это перекладывание решения downstream. H4 не может proceed с unresolved blocking вопросом независимо от того, кому он escalated.

### H3 revision detection

**Первое действие при каждом запуске H4** — читать поле `h3_elm_module_spec.revision_context` (если присутствует) и определить `run_context`.

```yaml

  revision_context_present: true/false
  downstream_rerun_required_contains_h4: true/false
  # true если revision_context.downstream_rerun_required включает "H4"
  h3_revision_requests_addressed: []
  # копия revision_context.requests_addressed (если present, иначе [])
  run_triggered_by_revision: true/false
  # true если revision_context_present: true AND downstream_rerun_required_contains_h4: true
```

**Если `run_triggered_by_revision: true`:**
- `run_number` = предыдущий `h4_elm_module_qa_report.run_number` + 1 (если предыдущий отчёт существует) или 1
- `run_context: rerun_after_h3_revision`
- `revision_source: h3_revision_request.yaml`
- `revision_requests_resolved`: copy from `h3_elm_module_spec.revision_context.requests_addressed`
- H4 **верифицирует** каждый request из `h3_revision_requests_addressed`: проверяет observable acceptance checks из `h3_revision_request.yaml`. Если acceptance check не выполнен → `spec_defect (significant)`.

**Если `run_triggered_by_revision: false` (revision_context отсутствует или не содержит H4):**
- `run_context: initial`, `run_number: 1`

**Revision request verification rule:**  
Для каждого `request_id` в `h3_revision_requests_addressed` H4 проверяет observable acceptance checks из `h3_revision_request.yaml` (секция `pending_requests[*].request_requirements[*].observable_acceptance_checks`). Верифицированные requests документируются в `revision_verification[]`. Невыполненный acceptance check → `spec_defect (significant)` с `recommendation: re-open h3_revision_request for unresolved request_id`.

## ЭТАП 2 — Coverage check

### 2A — Coverage matrix check

H3 содержит `coverage_matrix.surfaces[]` — primary coverage declaration. H4 использует её как первичный источник и cross-checks с modules.

```yaml
coverage_matrix_check:
  all_g21_approved_surfaces_present: true/false
  approved_surfaces_ownership_status_valid: true/false
  # approved: true → ownership_status должен быть assigned или speculative
  # approved: true + ownership_status: filtered_out допустим только если
  #   поверхность присутствует в source_conflicts (upstream inconsistency задокументирована)
  # approved: true + ownership_status: filtered_out без source_conflict → spec_defect significant
  # approved: true + ownership_status: unowned → spec_defect blocking
  speculative_approved_ownership_valid: true/false
  # approved: true + ownership_status: speculative → owning_module должен существовать
  #   и этот модуль должен иметь speculative: true + gap_assumptions заполнены
  # Отсутствие owning_module у speculative approved surface → spec_defect significant
  coverage_matrix_matches_modules: true/false
  # owning_module в coverage_matrix существует в соответствующей module group
  coverage_matrix_matches_routes: true/false
  # route_id для routable surfaces существует в route_definitions
  filtered_out_surfaces_documented_consistently: true/false
  # filtered_out в coverage_matrix ↔ запись в top-level filtered_out_surfaces[]
  inconsistencies: []                # {surface_id, inconsistency_type} → spec_defect significant
  finding: ok | spec_defect
```

### 2B — Module assignment check

Для каждого surface из G21 approved scope:
- Назначен ли routable surface в `modules.page_modules[].surfaces_owned`, а non-route surface — в top-level `non_route_surfaces[]` с валидным `ownership_module` и backref в `page_modules[].non_route_surfaces_owned` или `layout_modules[].non_route_surfaces_owned`?

```yaml
surface_coverage:
  approved_surfaces_total: <int>          # по G21
  surfaces_assigned: <int>
  surfaces_unowned: []                    # если непусто → spec_defect blocking
  non_route_surfaces_verified: <int>
  coverage_complete: true/false
  g21_h1_inconsistency: []               # расхождения G21 vs H1 → upstream_architecture_blocker
```

### 2C — Out-of-scope exclusion check

Surfaces вне G21 approved scope допустимы **только в**:
- `filtered_out_surfaces[]` (top-level)
- `coverage_matrix.surfaces` с `ownership_status: filtered_out`
- `source_conflicts[]`

Они **не должны** появляться в:
- `page_modules[].surfaces_owned` как активные surfaces
- `route_definitions` как основные surfaces (non-null surface_id)
- `flow_ownership_map[].surfaces_in_flow` без флага filtered/speculative + gap_assumption

```yaml
excluded_surfaces_check:
  out_of_scope_surfaces_correctly_filtered: []
  out_of_scope_surfaces_active_in_spec: []    # если непусто → spec_defect significant
  flow_map_out_of_scope_inadequate_flag: []
  # Для каждой out-of-scope surface в flow_ownership_map[].surfaces_in_flow:
  # требуются ОБА:
  # (a) coverage_matrix entry с ownership_status: filtered_out ИЛИ speculative
  # (b) gap_assumption существует на одном из уровней: flow entry, owning module, ИЛИ top-level H3
  # Если хотя бы одно из двух отсутствует → spec_defect significant
  finding: ok | spec_defect
```

### 3C — Platform-as-split check

**Определение нарушения:** `module_boundary_exception` документирует разделение одного surface на несколько модулей, и **единственным** обоснованием является платформа (mobile / web / breakpoint) — без структурной или функциональной разницы в ответственности. Примеры нарушения: "Separate Page for mobile because layout differs." Примеры НЕ нарушения: "Two modules because mobile has offline-first state machine and web does not", "Split because API contract differs per platform."

H4 ищет такие нарушения только в `module_boundary_exception` и `surface_analysis[*].platform_note`. Если платформенное различие упомянуто как один из факторов наряду с другими — нарушения нет.

```yaml
platform_split_check:
  platform_as_split_violations: []   # если непусто → spec_defect significant
```

## ЭТАП 4 — Support module policy check

**H3 использует `modules.support_modules[]`** (не `shared_modules`). Политика задаётся полем `extraction_policy`.

**Scope:** `support_policy_check` применяется **только** к `modules.support_modules[]`. Layout (`layout_modules`), Ports (`ports_module`), Main (`main_module`), Route (`route_module`), FlowCoordinator (`flow_coordinator_modules`) — в отдельных module groups; extraction_policy к ним не применяется.

| `extraction_policy` | Типы модулей в `support_modules` | Правило проверки |
|---|---|---|
| `infrastructural` | Session, Api | consumer_count criterion НЕ применяется |
| `consumer_count` | Shared, Component | `used_by_modules` count ≥ 2 или задокументировано исключение |
| `single_complex_domain` | Domain | сложный домен с явным обоснованием; consumer_count может быть 1 |
| `cross_cutting_concern` | любой | broad cross-cutting concern; consumer_count не требуется |

### 4A — Extraction policy correctness

```yaml
support_policy_check:
  - module_id:
    module_type:
    extraction_policy:
    consumers_listed: <int>
    policy_applied_correctly: true/false
    finding: ok | spec_defect
    severity: <если spec_defect>
```

### 4B — Required infrastructural modules

## ЭТАП 8 — Provisional/speculative markers check

### 8A — Unmarked provisional decisions

H4 не делает суждение "это решение должно быть provisional". Вместо этого проверяются **конкретные паттерны несоответствия** между `confidence: stable` и state полей в том же артефакте.

**Паттерн A — to_be_determined + stable:**
Поле внутри записи содержит значение `to_be_determined_by_h5`, `to_be_determined_by_h7`, `to_be_determined_by_h10`, или `to_be_determined_by_h12`, но `confidence` той же записи = `stable`.

*Примеры: `flow_ownership_map[].multi_step_state_location: to_be_determined_by_h5` + `confidence: stable`; `elm_packages_assumed.ports[].elm_event_owner_candidate: to_be_determined_by_h7` + `confidence: stable`.*

**Паттерн B — requires_hX_confirmation вложен в stable:**
Дочерний field имеет `confidence: requires_h5_confirmation`, `requires_h7_confirmation`, `requires_h10_confirmation`, или `requires_h12_confirmation`, но родительский блок помечен `confidence: stable`.

*Пример: `elm_architecture_style.session_architecture.confidence: requires_h5_confirmation` + `elm_architecture_style.confidence: stable`.*

**Паттерн C — "Hx to confirm" в тексте + stable:**
Текстовое поле (`rationale`, `gap_assumptions`, `open_question`) содержит фразу "Hx to confirm" или "confirmed by Hx" (x ∈ {5, 7, 10, 12}), но запись помечена `confidence: stable`.

Если ни один из трёх паттернов не обнаружен — ЭТАП 8A = ok. H4 не переклассифицирует `stable` на основании собственного суждения.

```yaml

  - location: <module_id или field path>
    pattern_detected: A | B | C
    claimed_confidence: stable
    evidence: <конкретное поле и его значение>
    finding: spec_defect
    severity: significant
```

## ЭТАП 11 — QA interpretation & H3 self-audit consistency

### 11A — QA interpretation

```yaml
qa_interpretation:
  h3_self_audit_reviewed: true/false
  h3_status_accepted: true/false
  h3_status_override: <если H4 не согласен со статусом H3>
  h3_open_questions_actioned: true/false
  gap_assumptions_valid: true/false
  gap_assumptions_disputes: []
```

**Gap assumption dispute rule — критерии несогласия:**

H4 фиксирует dispute только при наличии **позитивных свидетельств** из доступных артефактов. Три допустимых основания:

1. **Фактическое противоречие upstream:** assumption утверждает факт ("surface X not in scope"), который прямо опровергается G21, H1, или H2 (surface X listed as approved). Источник должен быть назван явно.
2. **Внутреннее противоречие в H3:** assumption противоречит другому полю того же H3 артефакта (например, assumption говорит "no auth needed" но route_definitions имеет `requires_auth: true`).
3. **Нарушение явного правила H3:** assumption применяет политику (например, consumer_count для infrastructural модуля), которая прямо запрещена правилами H3.

Если H4 не может верифицировать assumption из доступных артефактов — это **не** dispute. Это uncertainty, которую H4 документирует в `qa_interpretation.gap_assumptions_valid: false` без classify как spec_defect.

Classify как spec_defect (significant): только если одно из трёх оснований выше выполнено с явной ссылкой на источник.

### 11B — H3 self-audit consistency check

H4 сопоставляет ключевые H3 self-audit claims со своими находками.

**Checked flags (critical):**
- `self_audit.critical.all_approved_surfaces_assigned_to_module` → vs H4 surface_coverage.surfaces_unowned
- `self_audit.schema_validation.import_graph_acyclic` → vs H4 cycle_check.import_cycles
- `self_audit.critical.elm_packages_assumed_complete` → vs H4 closed_domains_check
- `self_audit.schema_validation.all_ports_module_port_ids_exist_in_ports` → vs H4 ports_mapping_check
- `self_audit.schema_validation.route_guard_consistency_valid` → vs H4 route_guard_consistency

Если H3 claims `true` на critical flag, но H4 находит significant/blocking defect → spec_defect (significant): H3 self-audit misleading.

**Scope:** H4 верифицирует только эти 5 критичных flags. Остальные H3 self-audit flags не проверяются H4 независимо — это намеренное ограничение, ограниченное зонами где H4 имеет собственные independent checks для сравнения.

```yaml
h3_self_audit_consistency_check:
  h3_claimed_true_but_h4_found_defect: []
  # {flag_path, h3_value: true, h4_finding, severity}
  h3_claimed_false_but_h4_passed: []
  # {flag_path, h3_value: false, h4_finding: pass}
  missing_expected_self_audit_flags: []
  # {flag_path, action: skip_check | significant}
  # Флаг отсутствует в H3 self_audit → H4 продолжает check независимо (не блокирует)
  # Если отсутствие критичного флага не позволяет верифицировать H3 self-audit → spec_defect significant
  misleading_critical_flags: []
  finding: ok | spec_defect
  severity: <если spec_defect: significant>
```

### Revision request artifact

При `proceed: false` из-за `spec_defect` findings (severity: blocking или significant), H4 **обязан также создать** `h3_revision_request.yaml` в той же директории `handoff/`.

**НЕ** создаётся для `upstream_architecture_blocker` findings сами по себе: UAB не делают `proceed: false`, а выходят через `passed_with_flags`, `downstream_impact` и `flags_for_downstream`. `h3_revision_request.yaml` нужен только для исправимых H3 `spec_defect` findings с severity `blocking` или `significant`.

```yaml
h3_revision_request:
  artifact_type: h3_revision_request
  target_agent: H3
  source_agent: H4
  source_artifact: h4_elm_module_qa_report.yaml

  status: open
  summary:
```

## Статусы

```
passed              — все checks пройдены; spec_defects отсутствуют;
                      нет upstream_architecture_blockers; proceed: true

passed_with_flags   — proceed: true; есть informational spec_defects и/или
                      upstream_architecture_blockers; нет significant/blocking defects;
                      либо execution_mode: degraded с заполненным degraded_checks;
                      flags_for_downstream должен быть непустым если любой UAB
                      затрагивает H5/H7/H10/H12

failed              — proceed: false; есть хотя бы один spec_defect с severity
                      blocking или significant; ИЛИ есть unowned approved surfaces

blocked             — execution_mode: blocked; h3_spec_present: false ИЛИ
                      h3_ready_for_h4: false ИЛИ g21_surface_list_available: false;
                      checks не выполнялись (кроме precondition_check)
```

## Ограничения

- H4 **не проектирует** module boundaries — только верифицирует H3.
- H4 **не принимает** решений об Elm types, Model, Msg — это H5.
- H4 **не штрафует** provisional decisions — только проверяет их маркировку.
- H4 **не смешивает** spec_defect и upstream_architecture_blocker.
- H4 **не включает** в scope surfaces вне G21 approved scope как active — только в filtered_out_surfaces.
- H4 **не переопределяет** gap_assumptions H3 без явного dispute с обоснованием.
- H4 **не штрафует** Elm-vocabulary в архитектурной части H3-артефакта — только конкретные type/Msg/Cmd конструкции в human-readable полях.
- H4 **не использует** surface count как критерий выбора routing package.
