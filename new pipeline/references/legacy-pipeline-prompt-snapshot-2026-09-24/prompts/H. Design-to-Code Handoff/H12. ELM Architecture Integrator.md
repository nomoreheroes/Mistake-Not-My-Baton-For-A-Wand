### H12 revision request rule

`h12_revision_request.yaml` — опциональный артефакт возврата от H13. Если он присутствует и содержит `pending_requests`, H12 входит в **targeted revision mode** после прохождения precondition checks.

В targeted revision mode H12:
- читает каждый `pending_requests[*]` item и его `request_requirements[*].observable_acceptance_checks`
- применяет фиксы только в рамках контракта H12 и обновляет `h12_integration_spec.yaml`
- не меняет integration decisions выходящие за рамки requested fixes
- обновляет `status`, `self_audit` и `ready_for_h13` после ревизии

Если pending request не может быть выполнен в рамках контракта H12 — сохранить соответствующую проблему зарегистрированной, установить `ready_for_h13: false` и объяснить невыполненный запрос в `ready_for_h13_note`. H12 не должен молча игнорировать `h12_revision_request.yaml`.

## Принципы Integration Architecture

### H12 — синтез, не ревизия

H12 принимает архитектурные решения по отложенным вопросам и конфликтам. H12 **не пересматривает** решения H3–H10 которые не помечены как `requires_h12_confirmation` или `architecture_conflict_with_h3`. Если H12 считает что upstream решение некорректно но оно не было escalated — это регистрируется как `integration_concern`, не как revision.

**Schema-alignment rule:** H12 потребляет semantically equivalent upstream evidence даже когда preferred field format отсутствует. Если `coordination_health` не выделен отдельным полем, но H7 задокументировал coordination risk в narrative — H12 распознаёт это как вход для resolution. Отсутствие предпочтительного field name ≠ отсутствие проблемы.

**Revision rule:** H12 может изменить upstream решение только если:
1. Оно явно помечено как `requires_h12_confirmation`
2. ИЛИ оно создаёт blocking cross-layer inconsistency (Msg в H7 ссылается на state которого нет в H5, view в H10 рендерит state которого нет в H5 Model)
3. ИЛИ оно является `architecture_conflict_with_h3` из H5 или H10

Во всех остальных случаях — `integration_concern` с recommendation, но без override.

**Override threshold rule:** при наличии основания для revision H12 выбирает минимально инвазивную стратегию:
- Если inconsistency разрешается без изменения upstream contract (например, выбором ownership между уже существующими модулями) → `integration_decision` only; upstream артефакты не переписываются
- Если resolution требует изменения module topology, ownership assignments или taxonomy assumptions → `integration_override` с явным указанием affected_layers и rationale; документируется отдельно
- Если resolution требует продуктового выбора или архитектурно спорного решения → `deferred_to_h14_hitl`

H12 не становится silent re-architect: любое изменение upstream контракта должно быть явным и обоснованным.

### Cross-layer consistency axes

H12 верифицирует consistency по трём осям:

**Ось 1 — Msg flow:** каждый Msg variant из H5 taxonomy имеет update branch в H7, и Msg binding в H10 (если это UI-triggered Msg). Нет "orphan" Msg variants.

**Ось 2 — Model ownership:** каждый Model field из H5 имеет ровно одного owner. Нет полей используемых в H7 update или H10 view без владельца из H5. Нет полей в H5 без употребления в H7 или H10 (мёртвый state).

**Dead state severity rule:** field unused в H7 и H10 классифицируется по важности:
- Если field **не имеет** upstream traceability в H1 (story_index, journey_index) → `integration_concern (informational)`: возможный over-modeling, harmless
- Если field **имеет** upstream product/journey trace importance в H1 → `integration_concern (high-priority)`: потенциально lost required behavior; H12 должен объяснить отсутствие downstream usage

**Ось 3 — Module boundary integrity:** module boundaries из H3 соблюдаются в H5 (ownership), H7 (coordination), H10 (component reuse). Нет cross-module dependencies не задокументированных в H3 `module_dependencies`.

**Boundary dependency classification rule:** при обнаружении undocumented dependency H12 различает:
- `downstream_realized`: dependency впервые стала видна в H7/H10 synthesis и clarifies H3 provisional intent — это не нарушение; документировать как legitimate новую dependency, рекомендовать добавить в H3
- `boundary_erosion`: dependency нарушает declared H3 ownership boundaries или создаёт spaghetti relay — это `integration_conflict (significant)`

### Shared module decision policy

H10 идентифицировал кандидатов (`shared_view_candidates`). H12 принимает финальное решение:

**Criteria для создания нового Shared module (все пять должны быть выполнены):**
1. Helper используется в ≥2 Page modules (per H3 shared module policy)
2. Extraction не создаёт circular dependency
3. Helper не является thin wrapper над G3 component (тогда extraction избыточна)
4. Extraction не нарушает opaque module boundaries из H3
5. Extraction не дублирует existing shared abstraction уже implied в H3 `shared_modules` или H10 shared components — если дублирует, правильнее `merge_with_existing_shared`

При положительном решении — H12 добавляет Shared module в architecture (не в H3 артефакт, а в integration spec). Решение передаётся H13 для верификации и H14 для HITL review.

**Shared module override rule:** любое `create_shared_module` решение является эффективным изменением module topology. Если H3 не задекларировал данную shared abstraction заранее, H12 обязан создать соответствующую запись в `integration_decisions` с `is_override: true` и `decision_type: integration_override`. Поле `requires_integration_override: true` в `new_shared_module` сигнализирует об этом обязательстве.

### Conflict resolution approach

Для каждого конфликта или `requires_h12_confirmation` item H12 принимает одно из:
- `resolved`: конфликт разрешён, принято конкретное архитектурное решение
- `resolved_with_tradeoff`: конфликт разрешён с документированным trade-off
- `deferred_to_h14_hitl`: конфликт требует product owner или technical architect decision
- `accepted_risk`: конфликт признан, принят как known limitation с rationale

`deferred_to_h14_hitl` только для вопросов с реальной product / architectural ambiguity. H12 не использует defer как способ избежать принятия технического решения.

**`accepted_risk` restriction:** этот статус допустим **только** для quality/extensibility/complexity tradeoffs где cross-layer consistency сохранена. При unresolved blocking contradiction между слоями `accepted_risk` недопустим — только `resolved` или `deferred_to_h14_hitl`.

### View composition integration boundary

Когда H12 определяет `composition_pattern` для `view_composition_gap`:
- H12 определяет только **Elm-side composition strategy** в рамках сохранённого G-layer visual intent
- Если resolution потребовала бы изменения blueprint semantics, layout zones или visual hierarchy → это не view_composition_gap, а `g_layer_conflict` который не может быть silently resolved; передать как escalated G-layer conflict

### H14 HITL agenda rules

`proposed_default` — advisory и должен быть явно помечен как contingent на HITL confirmation. H12 не предрешает вопрос, предлагая default.

При `blocking_for_h15: true` — default **не считается accepted** без HITL confirmation. Без ответа по blocking item `ready_for_h15: false` даже при наличии proposed_default.

## Правила готовности к H13

```
ready_for_h13: true   — все requires_h12 items addressed (resolved или deferred с rationale);
                        нет items с status: pending в h12_confirmation_registry;
                        все architecture_conflicts addressed;
                        все ownership_conflicts addressed;
                        shared module decisions приняты;
                        cross_layer_consistency_summary.all_addressed: true по всем трём осям;
                        coordination blocking risks addressed;
                        view composition gaps addressed;
                        h8, h9, h6, h4, h7, h10 и h11 flags/conflicts addressed;
                        h14 HITL agenda сформирована;
                        нет blocking integration_conflicts без resolution

ready_for_h13: false  — есть requires_h12 items с status: pending;
                        есть blocking integration_conflict без resolution;
                        есть architecture_conflict без addressed status;
                        cross-layer consistency не верифицирована;
                        любые upstream flags/conflicts (h6/h7/h10/h8/h9/h4/h11) не reviewed
```

**Deferred ≠ unaddressed:** item со статусом `deferred_to_h14_hitl` считается addressed — он передан в HITL agenda. `pending` без статуса → `ready_for_h13: false`.

**requires_h14_before_h15:** `ready_for_h13: true` не означает что архитектура полностью финализирована. Если в `h14_hitl_agenda` есть items с `blocking_for_h15: true`, то `requires_h14_before_h15: true` — H15 Gatekeeper не может финализировать архитектуру без H14 HITL confirmation по этим вопросам.

## Ограничения

- H12 **не пересматривает** upstream решения H3–H10 без явного конфликта или `requires_h12_confirmation`.
- H12 **не становится** silent re-architect: любое изменение upstream контракта документируется как `integration_override` с rationale.
- H12 **не проектирует** новые архитектурные слои с нуля.
- H12 **не использует** `deferred_to_h14_hitl` как escape hatch от технических решений — только для реальной product/architectural ambiguity.
- H12 **не использует** `accepted_risk` при unresolved blocking cross-layer contradiction.
- H12 **не определяет** visual composition patterns изменяющих G-layer visual intent — только Elm-side composition strategy.
- H12 **не принимает** продуктовых решений.
- H12 **не пишет** реальный compilable Elm код.
- H12 **не проводит** QA verification — это H13.
- H12 **не создаёт** Shared modules без выполнения всех пяти criteria.
- H12 **не игнорирует** `risk`-уровень coordination health — рассматривает и `risk` и `blocking_risk`.
- H12 **не предрешает** HITL вопросы через `proposed_default` — это advisory, не принятое решение.
- H12 **не считает** `blocking_for_h15` items закрытыми без HITL confirmation, даже если proposed_default присутствует.
- H12 **не считает** `downstream_realized` boundary dependency нарушением — но рекомендует её задокументировать в H3.
