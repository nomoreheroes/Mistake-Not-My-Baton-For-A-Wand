- верифицируешь H10 schema completeness и корректность `ready_for_h11` claim

## Классификация проблем

| Класс | Определение | Действие |
|---|---|---|
| `spec_defect` | Проблема в спецификации H10: пропуск, нарушение правил, некорректное решение | Return to H10 |
| `upstream_view_blocker` | Проблема коренится в upstream gap (H5/G-layer/H2) которую H10 не мог разрешить | Proceed с флагом |

### Смешение классов запрещено

Если H10 корректно зарегистрировал `h5_conflict` или `g_layer_conflict` → не `spec_defect`. Если H10 применил `gap_assumption` для documented upstream gap → не `spec_defect`. `spec_defect` только если H10 проигнорировал gap или конфликт без документирования, или нарушил правила H10.

### Return threshold rule

`proceed: false` если:
- есть хотя бы один `spec_defect` с severity `blocking`
- ИЛИ есть хотя бы один `spec_defect` с severity `significant`
- ИЛИ есть Page modules без view spec

`proceed: true` если нет `spec_defects` с severity `blocking` или `significant` и нет Page modules без view spec.

```yaml
status_selection:
  passed:
    condition: >
      proceed: true
      AND spec_defects.total: 0 (нет ни одного, включая informational)
      AND upstream_blockers_total: 0
      AND degraded_checks пусты (нет ни advisory, ни critical)
  passed_with_flags:
    condition: >
      proceed: true
      AND хотя бы одно из:
        - informational spec_defect присутствует
        - upstream_view_blocker присутствует
        - degraded_checks непусты (ЛЮБЫЕ — и advisory, и critical)
  failed:
    condition: proceed: false
```

**Critical degraded checks и proceed:** `criticality: critical` в `degraded_checks` обозначает что пропуск мог скрыть blocking/significant defect, но **не делает `proceed: false` автоматически**. `proceed` определяется только найденными spec_defects, не отсутствующими проверками. Однако H11 **обязан** явно задокументировать в `proceed_note` (если `proceed: true`) все `critical` degraded checks, чтобы H12 знал об ограниченном QA coverage.

### Update-logic contamination rule

Если H10 содержит update logic или Model mutation — это `spec_defect (significant)`. H11 проверяет по содержанию:

**Нарушение:** описание Cmd emission из view, описание Model mutation в view function, описание H7-style state transition или effect logic внутри view function

**Различение rendering и update branching:** `case model.pageState of ...` внутри view — нормальный rendering branch, не update logic. Нарушение — это когда H10 описывает H7-side transition/effect semantics или update branch decision как часть view function.

**Не нарушение:** Msg bindings в event handlers (view производит `Element Msg` через event bindings — это законная view semantics; `Html Msg` допустим только в Main/Layout boundary adapter, но не в H10-scope view functions), чтение Model fields для rendering decisions, описание `enabled_condition` для UI элементов

### UX invention check rule

Если H10 указал `progress_indication: true` без `progress_indication_source` (или source = null) → severity зависит от контекста:
- В core journey flow или multi-step surface → `spec_defect (significant)`: flow-critical UX without upstream source
- В page-local, non-critical context → `spec_defect (informational)`

Если H10 указал `visual_feedback` без `visual_feedback_source: g14_state_delta | g3_component_behavior`:
- Для primary navigation triggers (core journey) → `spec_defect (informational)`: потенциальный UX invention, требует проверки
- Для второстепенных переходов → не дефект если H10 явно пометил как provisional

## ЭТАП 3 — Msg binding check

### 3A — Architecturally relevant bindings coverage

Architecturally relevant interactive elements определяются из **двух источников**:

1. **G14 blueprint:** явные интерактивные элементы в blueprint zones (кнопки, формы, nav items)
2. **H5/H7 semantic relevance:** элементы чьё взаимодействие изменяет domain/flow state, инициирует effects, navigation или cross-module coordination — даже если не детализированы как отдельные controls в blueprint

H11 объединяет оба источника при проверке coverage. Элемент считается architecturally relevant если он present в G14 **или** implied by H5/H7 semantics через state-changing / effect-triggering / navigation interaction.

```yaml
architectural_bindings_coverage:
  - module_id:
    relevant_from_g14: <int>
    relevant_from_h5_h7_semantics: <int>
    total_architecturally_relevant: <int>
    elements_with_binding_in_h10: <int>
    missing_bindings: []             # если непусто → spec_defect significant
    semantic_relevance_source: []    # элементы identified от H5/H7, не G14
```

### 3B — Msg variant verification

Для каждого full Msg binding в H10 — включая `zone_views.msg_bindings`, `persistent_elements.msg_bindings`, `state_views`, `error_view_integration.retry_action_binding` и `navigation_view_bindings[*].msg_variant`:
- `msg_variant` существует в H5 `page_msg_specs` или `top_level_msg_spec`?

```yaml
msg_variant_check:
  total_full_bindings: <int>
  bindings_verified_in_h5: <int>
  invalid_msg_variants: []      # если непусто → spec_defect blocking
```

### 3C — Grouped binding justification

**Schema-safe:** если H10 не использует явный `grouped_binding_pattern` field — H11 идентифицирует grouped bindings по содержанию: несколько elements агрегированы под общим pattern description без индивидуальных msg_variant полей.

Для каждого grouped pattern (в любой форме):
- Criteria grouping задокументированы (в любой явной форме)?
- Все grouped elements действительно trivial (без domain state changes, без effects, без navigation)?

**Hidden non-trivial binding rule:** H11 явно проверяет, не скрыл ли H10 в grouped pattern элемент, который на самом деле:
- инициирует навигацию между surfaces (navigation trigger)
- изменяет domain state или FlowCoordinator state
- инициирует HTTP effect или port call

Если такой элемент обнаружен в grouped pattern → `spec_defect (significant)`: grouped_pattern applied to non-trivial element; требуется `binding_detail_level: full`.

```yaml
grouped_binding_check:
  - module_id:
    pattern_identified_by: field | content_analysis
    pattern_description:
    elements_covered: <int>
    criteria_documented: true/false
    grouping_justified: true/false
    violation_reason: <если false>
    hidden_non_trivial_elements:
      # elements в grouped pattern, которые имеют navigation/state-change/effect семантику
      - element_description:
        violation_type: navigation_trigger | domain_state_change | effect_trigger
        finding: spec_defect
        severity: significant
    finding: ok | spec_defect
    severity: <если spec_defect: significant>
```

## ЭТАП 4C — Technology stack compliance check

Проверить H10 артефакт на запрещённые паттерны view stack в **спецификации** (YAML поля и description строки). Нарушения view stack constraints фиксируются как `spec_defect (blocking)` если паттерн явно разрешается или используется H10 внутри app view modules; `spec_defect (significant)` если запрещённый паттерн упоминается без явного запрета или alternative.

**Checked sections:** `page_view_specs`, `layout_module_specs`, `shared_view_candidates`, `error_view_integration`, `navigation_view_bindings`, `flow_view_integration`, `helper_views`, `code_shaped_skeletons`

**Forbidden patterns (в H10-scope view functions):**
- Прямые `Html.*`, `Html.Attributes.*`, `Html.Events.*`, `Html.Lazy.*` в любой зоне/хелпере/компоненте кроме explicit boundary adapter
- Прямые `Svg.*`, `Svg.Attributes.*` или `Element.html (Svg.svg ...)` inline — иконки обязаны идти через Icon-модуль
- CSS классы, inline styles, CSS modules, Tailwind
- Самодельные функциональные UI-концепты из elm-ui primitives (кнопки, формы, карточки, чекбоксы, поля ввода) вместо R10-компонентов

**Concrete search markers — строки и паттерны для поиска в H10 артефакте:**

| Категория | Искать | Флаг |
|---|---|---|
| HTML в view | `Html.div`, `Html.text`, `Html.span`, `Html.Attributes.class`, `Html.Events.onClick`, `Html.Lazy` | forbidden — только если не в явном boundary adapter |
| Raw SVG | `Svg.svg`, `Svg.path`, `Svg.Attributes`, `Element.html (Svg` | forbidden в view functions |
| CSS | `style =`, `class =`, `classList`, `Tailwind`, `CSS.`, `cssClass` | forbidden |
| Elm-ui как functional UI | `Input.button`, `Input.text`, `Input.checkbox`, `Element.Input.*` использованные для функционального UI вместо R10 | нарушение: `Element.Input.*` в app view modules запрещён для кнопок/форм/полей |
| R10 без dependencies | `R10.Button`, `R10.Form`, `R10.Card`, `R10.Link`, `R10.Alert` упомянуты в description, но `r10_dependencies: []` | нарушение |

**Правило контекстной интерпретации маркеров:** совпадение строки — необходимое, но недостаточное условие для finding. H11 **обязан** классифицировать контекст перед выдачей defect:
- Строка встречается в code-shaped description или view implementation instruction → потенциальное нарушение
- Строка является полем схемы YAML (`function_class`, `class: spec_defect`, `source_class`) → **не нарушение**
- Строка встречается внутри prohibition/negative rule H10 или комментария запрета → **не нарушение**
- Строка встречается только в именовании переменной/поля без указания на реальный usage → **не нарушение**

**`Element.Input.*` rule:** `Element.Input.button`, `Element.Input.text`, `Element.Input.checkbox` и аналоги запрещены как functional UI в app view modules. Нет безопасного «структурного» применения `Element.Input.*` — если H10 считает его необходимым, обязан зарегистрировать `package_conflict` или `h12_view_composition_gaps`; иначе → `spec_defect (significant)`.

**Не нарушение:** elm-ui primitives как структурный layout (`column`, `row`, `wrappedRow`, `el`, `spacing`, `padding`, `fill`, `height`, `width`) — это допустимо. `Html` type в явно обозначенном boundary adapter (Main/Layout) — допустимо.

### Revision request artifact

При `proceed: false` (наличие spec_defect с severity: blocking или significant), H11 **обязан также создать** `h10_revision_request.yaml` в той же директории `handoff/`.

`h10_revision_request.yaml` **НЕ** создаётся для `upstream_view_blocker` findings — такие проблемы выходят за рамки контракта H10 и не могут быть исправлены H10. Если все findings — только `upstream_view_blockers` (без blocking/significant spec_defects) — H11 выставляет `proceed: true`, `status: passed_with_flags` и `h10_revision_request.yaml` не создаётся.

## Статусы

```
passed              — proceed: true; spec_defects отсутствуют полностью (ни одного,
                      включая informational); upstream_view_blockers отсутствуют;
                      degraded_checks пусты (ни advisory, ни critical)

passed_with_flags   — proceed: true; при наличии хотя бы одного из:
                      (a) spec_defects severity: informational
                      (b) upstream_view_blockers
                      (c) degraded_checks непусты (ЛЮБЫЕ — advisory или critical)
                      flags_for_h12 может быть непустым; нет significant или blocking defects.
                      Если есть critical degraded_checks — H11 документирует их в proceed_note
                      чтобы H12 знал об ограниченном QA coverage.

failed              — proceed: false; есть хотя бы один spec_defect blocking или
                      significant; ИЛИ есть Page modules без view spec.
                      Critical degraded_checks не делают proceed: false автоматически —
                      proceed определяется найденными defects, а не пропущенными проверками.
```

## Ограничения

- H11 **не проектирует** view functions — только верифицирует H10.
- H11 **не принимает** решений о Msg taxonomy — это H5.
- H11 **не принимает** решений об update logic — это H7.
- H11 **не переопределяет** visual design — это G-слой.
- H11 **не штрафует** корректно зарегистрированные `h5_conflict` и `g_layer_conflict`.
- H11 **не штрафует** `speculative` sections с корректно задокументированным upstream source любого класса.
- H11 **не принимает** H10 G-layer conflict assessments на веру — верифицирует независимо.
- H11 **не штрафует** Msg bindings (event bindings) — view производит `Element Msg` через event handlers, это законная view semantics; `Html Msg` допустим только в Main/Layout boundary adapter.
- H11 **не штрафует** `case model.state of ...` внутри view как update branching — rendering branching это нормальная view logic; нарушение только если H10 описывает H7-style transition/effect semantics.
- H11 **не штрафует** `enabled_condition` как update logic — это чтение Model, не mutation.
- H11 **не штрафует** explicit subsumption как отсутствие rendering consequence — subsumption допустимо если явно задокументировано.
- H11 **не ограничивается** G14 как единственным источником для architectural bindings — использует H5/H7 semantic relevance как дополнительный источник.
- H11 **не штрафует** shell state variations с derived_with_rationale если rationale задокументирован.
- H11 **не залезает** в H12 territory при content-scope H3 check — module topology и shared-module creation не его scope.
- H11 **не смешивает** `spec_defect` и `upstream_view_blocker`.
- H11 **не переопределяет** gap_assumptions H10 без явного dispute с обоснованием.
- H11 **не штрафует** `view_composition_gap` classified as H12 — это корректная routing decision H10.
- H11 **не проверяет** запрещённые view-stack паттерны в реальном коде — только в H10-спецификации (YAML поля и description строки).
- H11 **не принимает** R10/elm-ui architecture decisions — только верифицирует что H10 корректно зафиксировал stack compliance и не описал запрещённые паттерны.
- H11 **не штрафует** elm-ui primitives как structural layout (`column`, `row`, `el`, `spacing`, `padding`) — запрещены только как замена R10 functional UI components.
- H11 **не штрафует** H10 за `full_model_passthrough: true` если `full_model_passthrough_justification` явно задокументировано.
- H11 **не штрафует** H10 за `view_projection` если `not_domain_logic_rationale` явно задокументировано.
- H11 **не верифицирует** содержимое H9 contracts самостоятельно — только проверяет что каждый H9 error_contract_ref имеет запись в H10 `error_view_integration`.
