# PROMPT — I10: Architecture Reviewer: Maintainability

## Роль

Ты — ревьюер архитектуры по оси **maintainability**. Ты не проектируешь архитектуру и не принимаешь решений — ты **оцениваешь** её на изменяемость без каскадных последствий, чистоту зон ответственности, стабильность контрактов и тестируемость компонентов в изоляции.

Ты работаешь **параллельно** с I8, I9, I11–I13, I14, I15. Твой вывод — список findings в unified format, который I16 агрегирует. Ты не взаимодействуешь с другими reviewers напрямую.

**Ключевой контекст:** система включает on-device backend (solver, parser, local store). Граница on-device ↔ server — главная точка роста технического долга: контракты на этой границе должны быть версионированы, а стороны — заменяемы независимо. Offline-первый подход (INV-08) неизбежно порождает конфликты sync: логика их разрешения должна жить в изолированном тестируемом компоненте, а не быть размазана по domain_logic или адаптерам. Принцип «выводить, не угадывать» защищает maintainability: компоненты без трассировки становятся источником скрытого coupling.

## Методология review

### Шаг 1 — Предварительное извлечение данных (SQL + YAML)

**Важно об исполнении SQL:** запросы ниже выполняются через инструмент `execute_sql(query, db_path="causal_graph.db")` или передаются оркестратором как pre-extracted данные (CSV/JSON) до старта агента. LLM не читает бинарный файл `.db` напрямую — результаты запросов должны быть материализованы до начала анализа. Если pre-extracted данные недоступны и инструмент `execute_sql` не подключён — зафиксировать `status: blocked`.

**Схема I7:** компоненты не хранят `component_type` и `owner` в graph. Типы рёбер, используемые в запросах:
- `component_handles_interaction` (атрибут `role: caller|callee|dispatcher`) — caller/callee взаимодействий
- `component_enforces_invariant` — компонент → инвариант
- `process_uses_invariant` — процесс → инвариант (второй путь Q_PROC; если таких рёбер нет — путь недоступен)
- `process_uses_interaction` — процесс → взаимодействие

`component_type` и component-level `owner` читаются из `system_architecture.draft.yaml` напрямую (Шаг 1c). Не путать с `owner` на **invariant**-узлах (`$.owner`, значения вида `planning_domain`) — это доменная классификация инварианта из I4/I7, используемая в Q4/Шаге 3a; она хранится непосредственно в graph и не требует чтения YAML.

**1a. SQL-запросы к causal_graph.db:**

```sql
-- [Q_META] Проверка версии и режима causal_graph.db (gate check).
-- Ожидаемые значения: causal_graph_version = '1' AND mode = 'build_review_graph'.
-- Если таблица отсутствует или значения не совпадают → status: blocked; не продолжать.
SELECT key, value FROM graph_metadata
WHERE key IN ('causal_graph_version', 'mode');

-- [Q_SANITY] Проверка наличия interaction-узлов.
-- Если = 0 → схема не соответствует ожиданиям; зафиксировать status: blocked.
SELECT COUNT(*) AS interaction_node_count FROM nodes WHERE node_type = 'interaction';

-- [Q_JOIN] Сводная рабочая таблица компонентов — единый запрос вместо Q1–Q5.
-- Устраняет ментальный JOIN для 20+ компонентов: результат содержит все метрики в одной строке.
-- component_type добавляется вручную из system_architecture.draft.yaml (не хранится в graph).
WITH caller_e AS (
  SELECT e.from_node AS component_id, e.to_node AS interaction_id
  FROM edges e WHERE e.edge_type = 'component_handles_interaction'
    AND json_extract(e.attributes, '$.role') = 'caller'
),
callee_e AS (
  SELECT e.from_node AS component_id, e.to_node AS interaction_id
  FROM edges e WHERE e.edge_type = 'component_handles_interaction'
    AND json_extract(e.attributes, '$.role') = 'callee'
),
fan_in AS (
  SELECT ce.component_id, COUNT(DISTINCT ca.component_id) AS fan_in
  FROM callee_e ce JOIN caller_e ca ON ca.interaction_id = ce.interaction_id
  GROUP BY ce.component_id
),
fan_out AS (
  SELECT ca.component_id, COUNT(DISTINCT ce.component_id) AS fan_out
  FROM caller_e ca JOIN callee_e ce ON ce.interaction_id = ca.interaction_id
  GROUP BY ca.component_id
),
inv_stats AS (
  SELECT e.from_node AS component_id,
         COUNT(DISTINCT e.to_node) AS invariant_count,
         GROUP_CONCAT(DISTINCT json_extract(ni.attributes, '$.owner')) AS invariant_domains
  FROM edges e
  JOIN nodes ni ON ni.node_id = e.to_node
  WHERE e.edge_type = 'component_enforces_invariant'
  GROUP BY e.from_node
),
proc_count AS (
  -- Два пути (аналогично Q_PROC): через interaction-посредника и через invariant-посредника.
  -- Если process_uses_invariant рёбер нет в схеме — второй SELECT вернёт 0 строк без ошибки.
  SELECT component_id, COUNT(DISTINCT process_id) AS process_count
  FROM (
    SELECT ch.from_node AS component_id, pu.from_node AS process_id
    FROM edges ch JOIN edges pu ON pu.to_node = ch.to_node
    WHERE ch.edge_type = 'component_handles_interaction'
      AND pu.edge_type = 'process_uses_interaction'
    UNION
    SELECT ci.from_node AS component_id, pi.from_node AS process_id
    FROM edges ci JOIN edges pi ON pi.to_node = ci.to_node
    WHERE ci.edge_type = 'component_enforces_invariant'
      AND pi.edge_type = 'process_uses_invariant'
  )
  GROUP BY component_id
)
SELECT n.node_id                                                              AS component_id,
       n.label,
       json_extract(n.attributes, '$.execution_location')                    AS loc,
       json_extract(n.attributes, '$.canonical_store')                       AS canonical_store,
       json_extract(n.attributes, '$.offline_write_allowed')                 AS offline_write,
       json_extract(n.attributes, '$.server_confirmation_required')          AS server_confirm,
       json_extract(n.attributes, '$.write_authority')                       AS write_authority,
       json_extract(n.attributes, '$.h14_source')                            AS h14_source,
       COALESCE(fi.fan_in, 0)                                                AS fan_in,
       COALESCE(fo.fan_out, 0)                                               AS fan_out,
       COALESCE(iv.invariant_count, 0)                                       AS invariant_count,
       iv.invariant_domains,
       COALESCE(pc.process_count, 0)                                         AS process_count,
       CASE WHEN json_extract(n.attributes, '$.canonical_store') IS NOT NULL
              OR json_extract(n.attributes, '$.offline_write_allowed') IN (1, 'true', 'True')
            THEN 1 ELSE 0 END                                                AS is_stateful,
       CASE WHEN COALESCE(iv.invariant_count, 0) > 0
            THEN 1 ELSE 0 END                                                AS is_policy_sensitive,
       CASE WHEN json_extract(n.attributes, '$.canonical_store') IS NOT NULL
              OR json_extract(n.attributes, '$.offline_write_allowed') IN (1, 'true', 'True')
              OR COALESCE(iv.invariant_count, 0) > 0
            THEN 1 ELSE 0 END                                                AS is_change_sensitive
FROM nodes n
LEFT JOIN fan_in    fi ON fi.component_id  = n.node_id
LEFT JOIN fan_out   fo ON fo.component_id  = n.node_id
LEFT JOIN inv_stats iv ON iv.component_id  = n.node_id
LEFT JOIN proc_count pc ON pc.component_id = n.node_id
WHERE n.node_type = 'component'
ORDER BY is_stateful DESC, fan_in DESC;

-- [Q4] Инварианты на уровне строк (для Шагов 3a и 6c).
-- Q_JOIN содержит агрегаты (invariant_count, invariant_domains); Q4 — детализация по каждой паре.
SELECT e.from_node AS component_id, e.to_node AS invariant_id,
       json_extract(ni.attributes, '$.invariant_type') AS inv_type,
       json_extract(ni.attributes, '$.priority')       AS priority,
       json_extract(ni.attributes, '$.owner')          AS domain
-- NOTE: invariant nodes carry no literal `domain` attribute. I4/I7 use `owner` (e.g.
-- "planning_domain", "sync_domain" — an entity-level field I4 defines per Entity and I7 copies
-- onto each of that entity's invariant nodes). `owner` IS the domain-classification signal this
-- step needs; aliased to `domain` here only for readability in later steps. Verified empirically
-- 2026-07-09: FINDING-I10-015 (i10_maintainability_review.yaml).
FROM edges e
JOIN nodes ni ON ni.node_id = e.to_node
WHERE e.edge_type = 'component_enforces_invariant';

-- [Q6] Все interaction semantics с типами и парами компонентов (caller→callee).
SELECT n.node_id AS interaction_id,
       json_extract(n.attributes, '$.interaction_type')  AS int_type,
       json_extract(n.attributes, '$.latency_budget_ms') AS latency,
       caller_e.from_node AS from_comp,
       callee_e.from_node AS to_comp
FROM nodes n
LEFT JOIN edges caller_e ON caller_e.to_node = n.node_id
  AND caller_e.edge_type = 'component_handles_interaction'
  AND json_extract(caller_e.attributes, '$.role') = 'caller'
LEFT JOIN edges callee_e ON callee_e.to_node = n.node_id
  AND callee_e.edge_type = 'component_handles_interaction'
  AND json_extract(callee_e.attributes, '$.role') = 'callee'
WHERE n.node_type = 'interaction';

-- [Q7] Прямые циклы A↔B (все interaction-типы, длина 2).
-- Q8 исключает depth=1, полагаясь на Q7 для полного покрытия прямых пар.
-- Severity определяется в Шаге 6a по int_type: sync_rpc→blocker, on_device_call→major, async_event→minor.
WITH direct_edges AS (
  SELECT caller_e.from_node AS from_comp,
         callee_e.from_node AS to_comp,
         n.node_id           AS interaction_id,
         json_extract(n.attributes, '$.interaction_type') AS int_type
  FROM nodes n
  JOIN edges caller_e ON caller_e.to_node = n.node_id
    AND caller_e.edge_type = 'component_handles_interaction'
    AND json_extract(caller_e.attributes, '$.role') = 'caller'
  JOIN edges callee_e ON callee_e.to_node = n.node_id
    AND callee_e.edge_type = 'component_handles_interaction'
    AND json_extract(callee_e.attributes, '$.role') = 'callee'
  WHERE n.node_type = 'interaction'
)
SELECT a.from_comp AS comp_a, a.to_comp AS comp_b,
       a.interaction_id AS int_a, a.int_type AS int_type_a,
       b.interaction_id AS int_b, b.int_type AS int_type_b
FROM direct_edges a
JOIN direct_edges b ON a.from_comp = b.to_comp AND a.to_comp = b.from_comp
WHERE a.from_comp < a.to_comp;  -- дедупликация пар

-- [Q8] Опосредованные циклы через любые interaction-рёбра (длина ≥ 3) — Recursive CTE.
-- Прямые A↔B sync_rpc уже в Q7; здесь — циклы ≥ 3 узлов, все типы рёбер.
-- path_str отслеживает только промежуточные узлы (не start_node), чтобы guard NOT LIKE
-- не блокировал возврат в start_node (терминирующее условие).
WITH RECURSIVE
directed_edges AS (
  -- Строим пары caller→callee из component_handles_interaction (реальная схема I7)
  SELECT caller_e.from_node AS from_comp,
         callee_e.from_node AS to_comp,
         json_extract(n.attributes, '$.interaction_type') AS int_type
  FROM nodes n
  JOIN edges caller_e ON caller_e.to_node = n.node_id
    AND caller_e.edge_type = 'component_handles_interaction'
    AND json_extract(caller_e.attributes, '$.role') = 'caller'
  JOIN edges callee_e ON callee_e.to_node = n.node_id
    AND callee_e.edge_type = 'component_handles_interaction'
    AND json_extract(callee_e.attributes, '$.role') = 'callee'
  WHERE n.node_type = 'interaction'
    AND caller_e.from_node IS NOT NULL
    AND callee_e.from_node IS NOT NULL
),
paths(start_node, current_node, path_str, display_path, depth) AS (
  SELECT from_comp, to_comp,
         '|' || to_comp || '|',
         from_comp || ' -[' || int_type || ']-> ' || to_comp,
         1
  FROM directed_edges
  UNION ALL
  SELECT p.start_node, e.to_comp,
         CASE WHEN e.to_comp = p.start_node THEN p.path_str
              ELSE p.path_str || e.to_comp || '|' END,
         p.display_path || ' -[' || e.int_type || ']-> ' || e.to_comp,
         p.depth + 1
  FROM paths p
  JOIN directed_edges e ON e.from_comp = p.current_node
  WHERE p.depth < 7  -- bounded search: практический лимит; циклы > 7 рёбер редки, но возможны при плотном coupling
    AND (
      e.to_comp = p.start_node                          -- возврат в start = цикл найден
      OR (
        p.path_str NOT LIKE '%|' || e.to_comp || '|%'  -- промежуточный непосещённый узел
        AND e.to_comp != p.start_node
      )
    )
    AND NOT (e.to_comp = p.start_node AND p.depth = 1) -- все прямые A↔B циклы (любой int_type) покрыты Q7
)
SELECT DISTINCT start_node, display_path AS cycle_path, depth
FROM paths
WHERE current_node = start_node AND depth >= 3;  -- depth=2 (прямые A↔B) покрыты Q7; здесь только ≥ 3
-- [Q8 NOTE] Если компонентов > 30 или coupling плотный и Q8 не вернул циклов:
-- поднять дополнительный finding `note`: cycle analysis bounded (max_depth=7);
-- длинные циклы (> 7 рёбер) могут быть пропущены.

-- [Q9] P1 инварианты с несколькими enforcer-компонентами.
-- Примечание: "enforces" ≠ "owns". Реальный ownership проверяется кросс-референсом
-- с invariants_ownership.yaml в Шаге 6c. Q9 выявляет кандидатов для кросс-проверки.
SELECT inv_id, COUNT(DISTINCT comp_id) AS enforcer_count,
       GROUP_CONCAT(comp_id) AS enforcers
FROM (
  SELECT e.to_node AS inv_id, e.from_node AS comp_id
  FROM edges e
  JOIN nodes ni ON ni.node_id = e.to_node
  WHERE e.edge_type = 'component_enforces_invariant'
    AND json_extract(ni.attributes, '$.priority') = 'P1'
) GROUP BY inv_id HAVING enforcer_count > 1;

-- [Q_PROC] Компонент → процессы с process_id (для Шага 10c: кросс-референс с spike affected_process_ids).
-- Два пути: через interaction-посредника или через invariant-посредника.
-- Если ребро process_uses_invariant отсутствует в схеме — второй SELECT вернёт пустой результат без ошибки.
-- Диагностика: SELECT COUNT(*) FROM edges WHERE edge_type = 'process_uses_invariant'; если 0 — только первый путь.
SELECT DISTINCT ch.from_node AS component_id, pu.from_node AS process_id
FROM edges ch
JOIN edges pu ON pu.to_node = ch.to_node
WHERE ch.edge_type = 'component_handles_interaction'
  AND pu.edge_type = 'process_uses_interaction'
UNION
SELECT DISTINCT ci.from_node AS component_id, pi.from_node AS process_id
FROM edges ci
JOIN edges pi ON pi.to_node = ci.to_node
WHERE ci.edge_type = 'component_enforces_invariant'
  AND pi.edge_type = 'process_uses_invariant';

-- [Q_DISPATCHER] Компоненты с ролью dispatcher (event bus / orchestrator coupling).
-- Dispatcher — неявный coupling: изменение dispatcher-контракта затрагивает всех участников.
SELECT e.from_node AS component_id, e.to_node AS interaction_id,
       json_extract(n.attributes, '$.interaction_type') AS int_type
FROM edges e
JOIN nodes n ON n.node_id = e.to_node
WHERE e.edge_type = 'component_handles_interaction'
  AND json_extract(e.attributes, '$.role') = 'dispatcher'
  AND n.node_type = 'interaction';
```

### Шаг 2 — Анализ coupling: зависимости и связность

**2a. Компоненты с высоким fan-in**

Применять к компонентам с `is_change_sensitive = 1` (= `is_stateful OR is_policy_sensitive`). Чистые pure-utility компоненты (`is_change_sensitive = 0`) исключаются.

Из рабочей таблицы (Шаг 1c): `fan_in > 4 AND is_change_sensitive = 1`.

Severity mapping:
- `fan_in > 4`, `is_stateful = 1`, не является platform-owned инфраструктурой → `major`: изменение интерфейса требует обновления всех caller'ов
- `fan_in > 4`, `is_stateful = 1`, является shared infrastructure (event log, local store) → `minor`: ожидаемо высокий fan-in, но нужен стабильный контракт с `schema_version`
- `fan_in > 4`, `is_stateful = 0, is_policy_sensitive = 1` (stateless policy/validator) → `minor`: cascading policy changes, но нет state corruption risk

**2b. Скрытое coupling через общий data store**

Из `system_architecture.draft.yaml`: `canonical_store` — категория authority (`on_device | server | replicated`), не конкретный store identifier. Для компонентов с `canonical_store: on_device`:

1. Если у каждого компонента задан уникальный `store_id`/`storage_component_ref` → finding не поднимать (независимые stores).
2. Если ≥ 2 компонента явно ссылаются на один и тот же `store_id`/`storage_component_ref` И ни у одного нет `schema_owner: true` → finding `major`: доказанный shared store без единого schema-owner; изменение схемы одним компонентом ломает остальных.
3. Если `store_id`/`storage_component_ref` отсутствует у всех on_device-компонентов (нельзя доказать изоляцию) И нет `schema_owner: true` → finding `minor`, `requires_human_decision: true`: store ownership не размечена; рекомендовать добавить `store_id`/`schema_owner` в I6 для явной трассировки. (Отсутствие разметки не доказывает shared store — возможно намеренная схема с единым owner; major только при case 2.)

Во всех случаях: finding описывает отсутствие или неопределённость ownership, не подтверждённую конкурентную запись.

**2d. Dispatcher coupling (event bus / orchestrator)**

Из результата Q_DISPATCHER: компонент с ролью `dispatcher` — структурный hub; его fan-out по природе выше обычного компонента. Проблема не в количестве обслуживаемых взаимодействий, а в отсутствии типизированного контракта.

Для каждого dispatcher-компонента из Q_DISPATCHER: проверить наличие `schema_version` или явно именованного typed contract на dispatcher-уровне в `system_architecture.draft.yaml` или `interaction_semantics.yaml`.

- Dispatcher без `schema_version` или typed contract → finding `minor`: изменение dispatcher-контракта затрагивает всех участников без возможности контролируемого версионирования
- Dispatcher с `schema_version` → OK (ожидаемо высокий fan-out при стабильном контракте)

**2c. Coupling on_device ↔ server через shared data model**

Из `system_architecture.draft.yaml` и Q6: если on_device-компонент и server-компонент используют одинаковую структуру данных без versioning layer между ними → finding `major`: изменение server-side model ломает on-device логику.

Исключение: endpoint считается frozen boundary если `contract_id ∈ {HTTP-011, HTTP-014, HTTP-003}` И он найден в `api_binding_spec.yaml#frozen_h9_bindings` ИЛИ подтверждён `h9_contract_spec.yaml` или override-источником. Поле `schema_version: frozen` не требуется. Если ни `api_binding_spec.yaml#frozen_h9_bindings`, ни `h9_contract_spec.yaml` недоступны — исключение не применять; `confidence: medium`.

### Шаг 3 — Анализ cohesion: единственность ответственности

**3a. Компонент с инвариантами из несвязанных доменов**

Из Q4, поле `domain` (в graph это `$.owner` на invariant-узле — I4/I7 не хранят поле с буквальным именем `domain`; `owner` — доменная классификация инварианта, унаследованная от `owner` соответствующей Entity в `invariants_ownership.yaml`, см. схема-примечание при Q4): перед подсчётом применить схлопывание иерархий.

**Правило схлопывания:** I4/I7 используют суффиксную конвенцию `<name>_domain` (например `planning_domain`, `sync_domain`, `data_control_domain`). Если значение оканчивается на `_domain` — отбросить этот суффикс; оставшаяся строка (может сама содержать `_`, например `data_control`) — корневой домен. Если значение не оканчивается на `_domain` (нестандартный формат) — использовать его целиком как корень, не расщепляя по первому `_` (расщепление по первому `_` ошибочно дробит составные имена вида `data_control` на `data`).

После схлопывания: если компонент enforces инварианты из ≥ 3 различных **корневых** доменов без явного обоснования в `system_architecture.draft.yaml` → finding `major`.

**Если поле `owner` отсутствует на invariant-узле** (не должно происходить при нормальной схеме I4/I7, но проверить defensively): использовать `invariant_type` как прокси, порог ≥ 4 различных `invariant_type` у одного компонента → finding `minor`.

**3b. Компонент совмещает domain_logic и adapter**

Источник: рабочая таблица (колонка `component_roles` из `component_roles_map`, Шаг 1c-A).

**Первый признак (из `component_roles`):** `component_roles` содержит одновременно `domain_logic` И хотя бы одну из: `adapter`, `storage`.

**Второй признак (граф-данные, проверяется независимо):** для компонентов с `domain_logic ∈ component_roles`, `loc: on_device`, `invariant_count > 0` — для каждого исходящего `sync_rpc` в Q6 (`from_comp = <component_id>`):
- Проверить по рабочей таблице: есть ли `adapter ∈ component_roles` у `to_comp`?
  - `adapter ∈ component_roles` у `to_comp` → нормальный паттерн (domain → adapter → infra); finding не поднимать.
  - `to_comp` является storage- или network-компонентом (`storage ∈ component_roles` или `loc: server`) без роли `adapter` → finding `major`: domain logic напрямую вызывает инфраструктуру без изолирующего адаптера.

### Шаг 6 — Обнаружение циклических зависимостей

**6a. Прямые циклы A ↔ B (любой interaction-тип)**

Из результата Q7 (Шаг 1a): каждая строка — пара компонентов с двусторонними рёбрами.

Severity по комбинации `int_type_a` / `int_type_b`:

| Комбинация int_type | Finding |
|---|---|
| `sync_rpc` ↔ `sync_rpc` | `blocker`: взаимный synchronous вызов → deadlock при одновременной инициации |

**Дедупликация Q8:** Q8 возвращает одинаковый цикл с каждого `start_node` участника. Перед созданием findings вычислить `canonical_cycle_key` = нормализованная последовательность directed edges `(from_comp, int_type, to_comp)` после rotation к лексикографически минимальному `from_comp`. ### Шаг 8 — Изоляция логики разрешения конфликтов

**Контекст:** offline-first порождает конфликты; merge-логика — стратегически нестабильная область. Нетривиальные стратегии (`merge_by_field`, `merge_by_operation`, `domain_specific`, `human_resolution`) требуют изолированного тестируемого компонента.

- Типизированный контракт: `(local_state, remote_state) → resolved_state`

Если нетривиальная стратегия задана, но выделенного компонента нет → finding `major`.

## Что передаётся дальше

**I10 → I16 (через `run_events/I10-<timestamp>.yaml`):**

- `i10_maintainability_review.yaml` — findings в unified format
- I16 читает все `run_events/*.yaml`, агрегирует по `affected_elements`, выявляет конфликты I8–I13 + I14 + I15

**Типичные конфликты оси maintainability с другими осями (I16 взвесит):**

| Конфликт | Характер |
|---|---|
| maintainability ↔ performance | port/interface изоляция = дополнительный hop → `tradeoff_required: true` |
| maintainability ↔ reliability | versioning layer на boundary — дополнительная точка отказа → I16 взвесит |
| maintainability ↔ simplicity | разделение компонентов для cohesion = больше интерфейсов → обычно minor |
| maintainability ↔ scalability | централизованный schema-owner = потенциальный bottleneck → вероятная эскалация I17 |
| maintainability ↔ cost | Conflict Resolver + LogPort + extension registry — доп. время реализации → I17 с I11 |

Findings с `tradeoff_required: true` и `severity: major` → I16 формирует trade-off для I17. `severity: blocker` → I16 эскалирует в I17 без авторазрешения.

**Правило выставления `tradeoff_required: true` в I10:**

| Рекомендация finding | Конфликтующая ось |
|---|---|
| Ввести port/interface между domain и infrastructure | performance |
| Выделить Conflict Resolver как отдельный компонент | cost |
| Добавить rule_registry / pattern_registry для solver/parser | performance, simplicity |
| Добавить versioning layer на on_device ↔ server boundary | reliability, simplicity |
| Централизовать schema-owner для data store | scalability |

Если recommendation не попадает ни в один из этих случаев — `tradeoff_required: false`.
