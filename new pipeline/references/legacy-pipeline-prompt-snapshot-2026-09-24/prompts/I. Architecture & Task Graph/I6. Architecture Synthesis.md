### Шаг 2 — Вывести компоненты из процессов и инвариантов

**Правило деривации:** каждый компонент выводится из одного из трёх источников:

1. **Из процесса / группы процессов** — если несколько процессов разделяют `execution_location` и общие данные, они образуют компонент
2. **Из инварианта** — инвариант с `enforcement_mechanism: component` → компонент, который его реализует
3. **Из ребра interaction** — ребро `sync_rpc` без явного компонента-получателя → компонент-адаптер или контракт

**Алгоритм:**

```
Для каждого on_device-процесса или группы:
  → определить компонент с execution_location: on_device

Для каждого server-процесса или группы:
  → определить компонент с execution_location: server

Для инвариантов с enforcement_mechanism: component:
  → проверить, покрыт ли он уже выведенным компонентом
  → если нет → вывести новый компонент или добавить ответственность существующему

Для sync_rpc взаимодействий без receiver-компонента:
  → добавить адаптер или endpoint-компонент

Для async_event взаимодействий:
  → определить queue / event bus компонент если не покрыт
```

**Недопустимо:** вводить компонент только потому что "так принято в этой технологии".

**Правило трассировки (provenance_valid_if_any):** компонент считается обоснованным, если выполнено хотя бы одно из условий:

```yaml
provenance_valid_if_any:
  - derived_from_processes not empty   # выведен из process_id из I3
  - derived_from_invariants not empty  # выведен из invariant_id из I4
  - derived_from_interactions not empty # выведен из interaction IS_NNN из I5
  - h14_source not null                # явно предписан H14 HITL-решением
```

H14-компоненты, введённые по `h14_source`, обязаны дополнительно зафиксировать к каким process_id и invariant_id они относятся — если такая связь есть в уже накопленной модели. Если связи нет (например, platform_purchase_bridge — pure platform layer) → создать `open_question` типа `architecture_choice`, `blocking_level: blocks_task_generation`, с вопросом "какой процесс отвечает за этот компонент?". Это не блокирует синтез, но блокирует I20 в этой области.

**`h12_source` — трассировка к H12 integration_decisions (дополнительное поле, не отдельный источник `provenance_valid_if_any`).** Если компонент (уже обоснованный одним из четырёх источников выше) реализует или адресует запись `integration_decisions[]` из `h12_integration_spec.yaml` — зафиксировать `provenance.h12_source: [ID-NNN, ...]` (список: один компонент может закрывать несколько H12-решений, поэтому список, а не одиночное значение, в отличие от `h14_source`). Это единственный надёжный способ связать H12-решение с компонентом: поля `integration_decisions[].modules_affected`/`layers_affected` — имена модулей H-слоя, которые не обязаны и обычно не совпадают текстуально с `component_id` I-слоя (H12 запускается до синтеза I6-компонентов и физически не может знать их будущие имена). Без явного `h12_source` нижестоящая проверка (I23 Шаг 5g) вынуждена искать совпадение по имени модуля, которое на практике почти никогда не находится (в первом полном прогоне I23 все 18 H12-решений остались без `arch_refs` именно по этой причине и были засчитаны как gate failure, а не как «H12-решение не применимо к этой архитектуре»). Пройти по всем `integration_decisions[]` из `h12_integration_spec.yaml` и для каждого явно решить: адресован существующим компонентом (→ `h12_source` на этом компоненте) или не применим к этой архитектуре (→ зафиксировать это в `open_questions.yaml` как `architecture_choice`, а не молча пропустить).

**`h_layer_constraint_treatment` — секция `system_architecture.final.yaml` для H-констрейнтов без архитектурного соответствия.**

Когда H-констрейнт (H9/H12/H14) не имеет counterpart в I-архитектуре и это подтверждено решением I17 (вариант [A]), I6 фиксирует его в отдельной секции — она читается I23 Шагом 5g как architecture-level exemption и I20 при построении покрытия:

```yaml
h_layer_constraint_treatment:
  entries:
    - source_ref: h12_integration_spec.yaml#ID-001
      treatment: explicitly_not_applicable
      applies_to: architecture_conformance_only | architecture_and_implementation
      reason: "<почему у констрейнта нет I-layer counterpart — конкретно, не 'frontend-internal'>"
      decision_ref: ADR-I17-<NNN>
```

**Поле `applies_to` обязательно и по умолчанию `architecture_conformance_only`.** Это разграничение — прямое следствие реального дефекта прогона `I-run-20260618-001`: 19 H12/H14 frontend-решений были помечены `explicitly_not_applicable` («Elm/frontend-internal decision with no I-layer backend/on-device counterpart»), что верно для **архитектурного документа** — и одновременно молча исключило их из плана реализации, вместе со всем фронтендом.

Семантика:

- `architecture_conformance_only` — констрейнт не проверяется на соответствие компонентам архитектуры (`arch_refs` может быть пустым), но **остаётся обязательным к реализации**. I20 обязан отнести его к соответствующей поверхности из `surface_inventory[]` (см. I20, Шаг 1), I23 Шаг 5g проверяет наличие implementation-ссылки. Это значение применяется ко всем frontend-internal H-решениям: Elm module ownership, navigation effects, view reuse, port payload naming, routing mode, static rendering и т.п. — их обязан реализовать фронтенд, даже если I-архитектура о них ничего не знает.
- `architecture_and_implementation` — констрейнт снят полностью: он не проверяется ни архитектурой, ни реализацией. Допустим только когда решение I17 явно это утверждает (например: H-решение отменено, относится к отброшенной альтернативе, или дублирует уже реализованный констрейнт — с указанием какого). Требует непустого `reason`, объясняющего, почему реализация не нужна вовсе.

Запись без `applies_to` (устаревший формат) читается downstream как `architecture_conformance_only` — безопасный дефолт: констрейнт остаётся в покрытии реализации. I6 не пишет новые записи без явного `applies_to`.

**Критерии split / merge компонентов:**

Компонент необходимо разбить (`split_component_if`) если:
- Разные authority owner (разные владельцы данных)
- Разная граница failure isolation (отказ одной части не должен ронять другую)
- Разный deployment / update cadence (обновляются независимо)
- Разная security / privacy boundary (разные требования к доступу)
- Разный scaling profile
- sync/async граница пересекает durability requirement

Компоненты можно объединить (`merge_component_if`) если:
- Одинаковый `execution_location`
- Одинаковая authority model
- Одинаковый lifecycle
- Нет независимого failure recovery
- Нет отдельного contract boundary

### Шаг 3 — Назначить execution_location каждому компоненту

Каждый компонент получает одно из трёх значений:

```
on_device  — solver, parser, local store, local state machine, chat inline confirm, local delete handler
server     — sync endpoint, push, cloud delete, stripe adapter
hybrid     — компонент с on-device логикой и server-sync (если явно выводится из I5)
```

**Правило для offline-режима (INV-08):** offline-первичность — архитектурное требование. On-device компоненты проектируются так, что работают без сети.

**Запрет на hybrid как мусорную категорию:** `hybrid` допустим только если выводится явно из I5 (есть конкретные on_device_call + sync_rpc ребра для одного компонента). Каждый `hybrid`-компонент обязан разложиться на явные части:

```yaml
hybrid_component:
  component_id: task_sync_manager
  execution_location: hybrid
  offline_part:
    responsibilities: [queue_pending_changes, apply_local_edits]
    enforced_invariants: [INV_08]
    works_without_network: true
  online_part:
    responsibilities: [push_events_to_server, receive_server_ack]
    interactions: [IS_003, IS_007]
  degradation_mode:
    when_network_unavailable: continue_offline_part_only
    pending_changes_behavior: queue_in_local_event_log
    recovery_on_reconnect: replay_queue_then_ack
```

Если описать `offline_part` и `online_part` не получается — принудительный split:

```yaml
hybrid_forced_split:
  trigger: "offline_part или online_part не поддаётся формализации"
  action: split_component
  result:
    - component_id: <original_id>_local_cache
      execution_location: on_device
      responsibility: локальное хранение + чтение без сети
    - component_id: <original_id>_sync_adapter
      execution_location: server     # или hybrid с явной on/off boundary
      responsibility: синхронизация изменений с сервером
  interaction_between_parts:
    type: async_event                # локальный кеш публикует событие → адаптер отправляет
    delivery: durable_queue_required # pending_changes должны пережить offline
  note: "Не создавать open_question для HITL — это детерминированное архитектурное решение."
```

Исключение: если неясно, что входит в offline_part по причине product_policy (например, "какие данные доступны offline?") → это `open_question` типа `product_policy`, `resolution_mode: human_required`, `blocking_level: blocks_specific_component`. В этом случае split не выполняется до резолюции.

### Шаг 5 — Записать authority model в компоненты

Один компонент часто управляет несколькими сущностями с разными authority rules (например: локальные задачи, cloud account data, payment entitlement, delete state). Authority model задаётся **на уровне entity_id**, не на уровне компонента целиком.

Для каждого компонента, работающего с данными:

```yaml
component:
  component_id: task_store
  execution_location: on_device
  authority_by_entity:
    - entity_id: TASK                  # из invariants_ownership.yaml (I4)
      canonical_store: replicated
      write_authority: device
      conflict_resolution:
        strategy: merge_by_operation
        condition: null
      sync_requirement: eventual
      offline_write_allowed: true
      server_confirmation_required: false

    - entity_id: CLOUD_ACCOUNT_DATA   # из invariants_ownership.yaml (I4)
      canonical_store: server
      write_authority: server
      conflict_resolution:
        strategy: server_wins
        condition: on_delete
      sync_requirement: immediate
      offline_write_allowed: false
      server_confirmation_required: true
```

**Правило:** для каждого `entity_id` в `authority_by_entity[]` должна существовать соответствующая запись в `invariants_ownership.yaml` (I4). Если записи нет — это `open_question` типа `domain_fact`, `blocking_level: blocks_specific_component`.

**Обязательно из H14 HITL-002:** entity, связанная с cloud delete, обязана иметь:

```yaml
- entity_id: CLOUD_ACCOUNT_DATA
  canonical_store: server
  offline_write_allowed: false
  server_confirmation_required: true
  conflict_resolution:
    strategy: server_wins
    condition: on_delete
```

### Шаг 6 — Выявить spike candidates

Spike candidate генерируется **только** для `open_question` с `type: technical_unknown` и `resolution_mode: spike_allowed`.

Перед созданием spike I6 обязан выполнить `decision_gap_screen`:

```yaml
decision_gap_screen:
  is_missing_upstream_decision: true | false
  missing_decision_owner: I2 | H14/HITL | H-layer | null
  missing_contract_fields: []
  evidence_can_be_created_by_spike: true | false
  new_evidence_sources:
    - benchmark | PoC | automated_test | vendor_docs | external_research
  project_docs_only: true | false
  routing_result: create_spike | return_to_upstream_decision
```

Если `is_missing_upstream_decision: true` или `project_docs_only: true` при отсутствии benchmark/PoC/test/external evidence → `routing_result: return_to_upstream_decision`; spike_candidate **не создавать**.
Для performance/latency вопросов это обязательное правило: если upstream задал только p95/p99, но downstream validation требует worst-case/timeout, это `architecture_choice` с `resolution_mode: architect_decision_allowed` и `upstream_target_agent: I2`, а не `technical_unknown`.

**Mandatory upstream-contract classifiers:**

- If any affected `sync_rpc` interaction lacks `timeout_ms`, `timeout_source`, timeout budget, measurement boundary,
  endpoint-specific timeout policy, or retry/idempotency semantics, classify the gap as
  `is_missing_upstream_decision: true`, `missing_decision_owner: I2`, `evidence_can_be_created_by_spike: false`,
  `project_docs_only: true`, `routing_result: return_to_upstream_decision`. Do not create a research spike.
- If any cross-boundary or durable `async_event` interaction lacks `auth_context.mechanism`, event envelope schema,
  auth proof, authority direction, replay/idempotency policy, audit metadata, dead-letter semantics, or consumer trust
  boundary, classify it the same way: I2/HITL must define the upstream architecture contract first. A spike may validate
  implementation viability only after that contract exists.

**Запрещено** генерировать spike для:
- `product_policy` → только HITL
- `legal_security_constraint` → только HITL
- `architecture_choice` → HITL или I2
- `domain_fact` → assumption
- missing/mismatched upstream architectural contract (например, p95 budget есть, но worst-case/timeout contract отсутствует) → вернуть в I2/HITL
- documentation-only self-research, где единственные evidence sources — уже созданные project artifacts и нет нового измерения, PoC, теста, vendor docs или external research

**Формат spike_candidate:**

```yaml
spike_candidate:
  spike_id: SPIKE-001
  question: "Can CRDT-based merge work for our task structure?"
  type: technical_unknown
  open_question_id: OQ-I5-XXX      # источник вопроса

  provenance_category: upstream_requirement | i_layer_initiative
  # upstream_requirement: spike порождён требованием из H/D-слоёв
  # i_layer_initiative: spike порождён архитектурным решением внутри I-слоя

  decision_gap_screen:
    is_missing_upstream_decision: false
    missing_decision_owner: null
    missing_contract_fields: []
    evidence_can_be_created_by_spike: true
    new_evidence_sources: [benchmark]
    project_docs_only: false
    routing_result: create_spike

  research_method: benchmark | PoC | automated_test | vendor_docs | external_research
  acceptance_criteria:
    - "<measurable criterion that can accept/reject the assumption>"
  evidence_sources:
    - "<source capable of producing new evidence; not only generated project docs>"

  impact_radius:                   # компоненты, которые затронет провал spike
    - solver_component
    - local_event_log_component

  affected_process_ids:            # из process_causality_map.yaml
    - PROC_007
    - PROC_012

  affected_invariant_ids:          # из invariants_ownership.yaml
    - INV_003

  affected_interaction_ids:        # из interaction_semantics.yaml
    - IS_004

  blast_radius: architecture_global | component | optimization
  # architecture_global: провал может разрушить архитектуру целиком
  # component: провал затрагивает один или несколько компонентов
  # optimization: известен fallback, spike только об оптимизации

  dependent_tasks: []              # пока пустой; I20 заполнит
  research_task_id: null           # I20 заполнит

  publish_policy:
    architecture_global: defer_implementation   # I20 не материализует impl-задачи
    component: block_dependent_tasks
    optimization: publish_with_risk_flag

  status: open
```

**Определение blast_radius:**

- `architecture_global` — выполняется хотя бы одно из:
  - `impact_radius` содержит > 2 несвязанных компонентов (нет общего data flow или ownership)
  - spike затрагивает инвариант из категории **ядровых**: `enforcement_mechanism: architecture` ИЛИ
    инвариант явно связан с offline-first (INV-08) / sync_protocol / conflict_resolution /
    data_loss_prevention (любой инвариант, при нарушении которого теряются данные пользователя)
  - spike затрагивает frozen_api_surface контракт (требует изменения H9 → layer_rollback territory)

- `component` — все условия выполнены:
  - `impact_radius` содержит ≤ 2 компонентов
  - ни один из них не является ядровым инвариантом (выше)
  - известен конкретный fallback без spike (архитектура продолжает работать при провале)

- `optimization` — выполняется:
  - текущая архитектура функционально корректна без spike
  - spike исследует только качество (latency, throughput, memory) — не корректность

Если граница между `component` и `architecture_global` неоднозначна → выбрать `architecture_global` (консервативный путь).

    component_ids: []
    process_ids: []
    invariant_ids: []
  upstream_target_agent: I2 | H14/HITL | H-layer | null
  missing_contract_fields: []       # для decision gaps: metric, scope, timeout, worst_case_ms, etc.

Технические неизвестные с `spike_allowed` → одновременно создать spike_candidate (Шаг 6) только если `decision_gap_screen.routing_result == create_spike`.
Если screen возвращает `return_to_upstream_decision`, НЕ переписывать чужой OQ-I3/I4/I5. Создать новый OQ-I6 wrapper с `source_question_id`, `type: architecture_choice`, `resolution_mode: architect_decision_allowed`, заполнить `upstream_target_agent`, `missing_contract_fields`, `spike_forbidden_reason`, и НЕ создавать spike_candidate.

**Decision tree для неопределённостей (uncertainty_routing):**

Когда I6 встречает неопределённость — выбрать ровно один путь:

```yaml
uncertainty_routing:
  use_assumption_if:
    - архитектура может продолжаться безопасно без ответа на вопрос
    - известен fallback при ошибочном допущении
    - есть конкретный validation_stage (I14/I15/I18), который проверит допущение
    → action: добавить в assumptions.yaml (Шаг 8)

  use_open_question_if:
    - безопасный архитектурный выбор невозможен без ответа
    - требуется продуктовое, security или legal решение (human_required)
    - выбор между двумя архитектурными подходами (architect_decision_allowed)
    → action: добавить в open_questions.yaml (Шаг 7)

  use_spike_candidate_if:
    - вопрос имеет type: technical_unknown
    - resolution_mode: spike_allowed
    - эмпирическая проверка возможна (код, тест, PoC)
    - вопрос не является missing upstream decision / contract mismatch
    - spike создаёт новое evidence: benchmark, PoC, automated_test, vendor_docs или external_research
    - acceptance_criteria измеримы и могут принять/отклонить assumption
    → action: создать open_question (Шаг 7) + spike_candidate (Шаг 6)

  return_to_upstream_decision_if:
    # Это не spike, а отсутствующий архитектурный/продуктовый контракт.
    - вопрос требует выбрать приемлемый contract, policy, metric, timeout, SLA/SLO или scope
    - upstream artifacts содержат только другую метрику (например p95/p99), а downstream rule требует worst-case/timeout
    - ответ нельзя получить чтением уже созданных project artifacts
    - без нового решения benchmark/PoC может только измерить значение, но не сказать, приемлемо ли оно
    → action: создать OQ-I6 wrapper с `source_question_id` на исходный вопрос:
      type: architecture_choice
      resolution_mode: architect_decision_allowed
      upstream_target_agent: I2
      spike_forbidden_reason: missing_upstream_architectural_contract
      blocking_level: blocks_architecture если затронуты архитектурный класс/много interactions; иначе blocks_specific_component
    → НЕ создавать spike_candidate

  edge_case_technical_unknown_no_spike:
    # Техническая неизвестность, где spike невозможен:
    # — ответ требует от внешней системы или вендора (SDK версия, платформенное API, лицензия)
    # — нет кода, который можно написать для проверки; нужен внешний ответ
    condition:
      - type: technical_unknown
      - resolution_mode: human_required   # spike невозможен — внешняя зависимость
    action: создать open_question с resolution_mode: human_required
    # НЕ создавать assumption — внешняя зависимость не может быть допущением
    # НЕ создавать spike_candidate — спайком это не проверить
    blocking_level: "blocks_architecture если без ответа нельзя выбрать компонент; иначе blocks_specific_component"
    example: "Поддерживает ли StoreKit 2 отмену транзакции после подтверждения биометрии?"
```

**Запрещено:** одновременно создавать assumption и open_question для одной и той же неопределённости. Если сделано допущение — вопрос закрыт как `converted_to_assumption`.
