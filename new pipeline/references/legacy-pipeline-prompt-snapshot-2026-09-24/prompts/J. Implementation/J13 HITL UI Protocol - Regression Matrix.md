# J13 HITL UI Protocol — Regression Matrix

Обязательный набор сценариев перед принятием контракта J13/J0/J6/J10/J11 в эксплуатацию. Каждый сценарий — конкретное состояние на входе и **один** детерминированный ожидаемый результат, со ссылкой на механизм в исходных файлах, который обязан его обеспечить. Сценарий, у которого на входе одно состояние, а на выходе два разных возможных результата в зависимости от неуказанного условия, не проходит этот бар — он либо переформулируется с уточнённым входом, либо разбивается на несколько сценариев (см. #8A/#8B, #12A/#12B ниже — оба возникли из ревизии первой версии этой матрицы, где такая двусмысленность была найдена).

Это не замена интеграционных тестов реализации — это чек-лист того, что сама спецификация (`J13. HITL UI.md`, `J0. Dispatcher.md`, `J6. Coder.md`, `J10. Code Analyst.md`, `J11. Documenter.md`) действительно определяет поведение для каждого случая однозначно, без места для двух прочтений.

Статус колонки: каждый сценарий должен быть прогнан против фактической реализации перед приёмкой; эта таблица фиксирует ожидаемый результат, не факт его проверки.

**Эта матрица никогда не нормативнее `J0. Dispatcher.md`/`J13. HITL UI.md`/`J6. Coder.md`/`J10. Code Analyst.md`/`J11. Documenter.md` — runtime-контракты являются единственным source of truth.** Если формулировка сценария здесь расходится с тем, что реально определяют эти файлы (включая случай, когда сама спецификация с тех пор изменилась, а этот документ отстал) — расхождение само по себе не делает поведение неопределённым; контракты выигрывают, а эта таблица считается устаревшей и требует правки, никогда наоборот. Release-blocker — только расхождение самих контрактов друг с другом; расхождение матрицы с уже-непротиворечивыми контрактами — обычный technical debt этого документа, не блокер.

## Терминология: три множества артефактов, и почему terminal markers — не плоский набор из четырёх взаимозаменяемых элементов

Предыдущая редакция этого документа один раз перечислила `hitl_ui_launch_blocked_*` вместе с `result`/`abandoned`/`invalidated`/`orphaned` как «terminal artifact set» — притом что в этом же документе `launch_blocked` прямо назван транзитным, non-consuming. Отдельно, первая версия этого раздела использовала правило «больше одного terminal marker → всегда `session_artifact_conflict`» — но `invalidated` **по конструкции** пишется ПОВЕРХ уже существующего `result` (Post-Result Integrity Failure обнаруживается уже ПОСЛЕ того, как result записан — см. `J0. Dispatcher.md`, "Post-Result Integrity Gate"), и оба, `result` и `invalidated`, permanent и никогда не удаляются. Значит `result + invalidated` — это два terminal marker'а одновременно, и это совершенно штатное, ожидаемое состояние (см. сценарии #9/#10), а не конфликт. Наивное «count > 1 → conflict» правило само себе противоречило.

Правильная модель — **base terminal marker + overlay**, а не плоское множество из четырёх равноправных элементов:

```
base terminal markers = { result, abandoned, orphaned }
  # ровно один из этих трёх может существовать для данного session_id — они взаимоисключающие
  # исходы одной и той же логической сессии (успешно/отклонённо разрешена, заброшена навсегда,
  # или baseline потерян до того, как round 2 вообще стал возможен).

terminal overlay = { invalidated }
  # пишется ПОВЕРХ уже существующего result (никогда самостоятельно, никогда поверх
  # abandoned/orphaned) — постфактум-обнаруженная утрата доверия к уже записанному result.

transient_control_artifacts = { launch_blocked }
  # non-consuming, housekeeping-only (см. J13.md, Launch Conditions) — не потребляет
  # session_id, может быть удалён/проигнорирован при следующей попытке, и никогда
  # не входит в модель terminal/base/overlay ниже.

request  # отдельный durable, НЕ-terminal session artifact — существует с момента
         # status: opening/open, сам по себе не завершает сессию. Round-1 Preflight-блок —
         # единственный случай, где result существует, а request — нет вообще (request_ref: null).

invocation_candidate_artifacts = { result_candidate, abandoned_candidate }
  # физические файлы hitl_ui_result_<session_id>__<hitl_ui_invocation_id>.yaml /
  # hitl_ui_abandoned_<session_id>__<hitl_ui_invocation_id>.yaml — это то, что J13 реально
  # пишет (см. J13.md, Allowed Actions); канонические result/abandoned из base terminal markers
  # выше — это то, во что J0 их промоутит. Свойства: immutable; invocation-scoped (никогда не
  # переиспользуют hitl_ui_invocation_id); НЕ terminal marker сами по себе — существование
  # candidate само по себе не потребляет session_id и не входит в таблицу состояний ниже;
  # никогда не используются напрямую для routing/merge; только J0, под своим текущим fenced
  # lease, может промоутить ровно ОДИН candidate конкретной сессии в соответствующий base
  # terminal marker (см. J0. Dispatcher.md, "Candidate reconciliation" / Promotion) — после чего
  # candidate становится disposable housekeeping, как launch_blocked. Recovery обязан
  # реконциллировать текущий candidate (если есть) ПЕРЕД оценкой состояния сессии по таблице
  # ниже (см. #N27/#N28/#N29) — иначе ещё не промоутнутый candidate может привести к
  # неправильной классификации сессии.

promotion_coordination_artifacts = { terminal_claim }
  # физический файл hitl_ui_terminal_claim_<session_id>.yaml (см. J0. Dispatcher.md, Promotion
  # шаг (c2)) — J0-owned; координирует promotion/recovery между тремя взаимоисключающими base
  # terminal kind'ами (result/abandoned/orphaned), разделяя один и тот же claim-slot между ними,
  # так что per-filename atomic-create по отдельности не может дать двум разным kind'ам
  # независимо "выиграть". НЕ base terminal marker сам по себе; НЕ acceptance/routing-артефакт;
  # может быть load-bearing во время незавершённого promotion (crash между Promotion шагами (d)
  # и (e) — см. #N30) — в этом окне claim физически на диске, но сессия ещё не durably terminal.
  # Reconciled ПЕРЕД обычным session-state recovery, тем же принципом, что и invocation candidate
  # выше (см. Promotion шаг (b), claim-aware conflict check).
```

Допустимые состояния (см. `J0. Dispatcher.md`, recovery-таблица — источник истины, откуда взята эта модель):

| `request` | base marker | overlay (`invalidated`) | Состояние |
|---|---|---|---|
| нет | нет | нет | сессия ещё не открывалась / не дошла до записи request |
| нет | `result` (`request_ref: null`, round-1 Preflight block) | нет | `concluded_round1_preflight` |
| нет | `result` (`request_ref: null`) | да | `invalidated_round1_preflight` — result не заслуживает доверия |
| да | нет | нет | `awaiting_round2` — ещё ждёт round 2, безопасно возобновить |
| да | `result` | нет | `concluded_result` |
| да | `result` | да | `concluded_invalidated` — result не заслуживает доверия, никогда не мержить |
| да | `abandoned` | нет | `concluded_abandoned` — брошено навсегда, никогда не возобновлять |
| да | `orphaned` | нет | `concluded_orphaned` — baseline потерян, никогда не возобновлять |
| любая другая комбинация (два разных base marker'а одновременно; `invalidated` без `result`; `invalidated` вместе с `abandoned`/`orphaned`; и т.п.) | | | `session_artifact_conflict` — fail closed, ни один marker не выбирается победителем |

`transient_control_artifacts` (`launch_blocked`) никогда не входят в эту модель ни в одну сторону — присутствие `launch_blocked_*` не делает сессию "concluded" и не участвует в определении состояния выше (см. #N23).

## Область применения

Эта матрица покрывает **только** протокол J13 HITL-UI (сессии, artifacts, durable state, merge) и его прямых потребителей (J0, J6, J10, J11, J4). I-слой не входит в область действия — по давнему решению, зафиксированному для этой версии пайплайна: I-слой не анализируется и не изменяется здесь. Название документа отражает это: тестируется весь протокол HITL UI сессии, а не только промпт одного subagent'а.

## Как использовать

Каждая строка — отдельный тест-кейс (unit/integration, в зависимости от того, насколько глубоко тестовая инфраструктура может симулировать crash-windows и конкурентную запись). Строка считается закрытой только когда: (а) тест реально воспроизводит "дано" на реальных или замоканных артефактах, (б) наблюдаемый результат совпадает с "ожидаемым результатом" колонки **полностью, включая любые дополнительные поля вроде `eligible_for_acceptance_merge`**, не только `session_outcome`, (в) при несовпадении — фиксится сам контракт (файлы выше), а не тест подгоняется под фактическое поведение.

## Что сознательно не входит в обязательную матрицу

Не раздувать эту матрицу тестами на каждую косметическую разновидность одного и того же механизма отказа — для этого предназначены property-based/schema-тесты, не regression matrix:

- каждое отдельное значение `participant_ref`/`actor_role`;
- каждая разновидность PII/секрета, которую ловит Bundle Sanitization Pass;
- все комбинации `device_viewport_build_ref`;
- каждая допустимая `rejection_category`;
- все Windows-reserved имена файлов по одному;
- десятки вариантов одного и того же malformed-хеша (не-hex, неверная длина, и т.п.).

Регрессионная матрица ловит разные **механизмы** отказа, а не исчерпывает все возможные входные строки.
