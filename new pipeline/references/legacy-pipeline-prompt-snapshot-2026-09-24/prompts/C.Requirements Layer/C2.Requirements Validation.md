# STAGE 0.5 — Build Merged Aspect Index

## Критически важно

`concept_coverage_map.yaml` содержит **только базовые аспекты B1**.
Аспекты B2–B6 находятся исключительно в patch-файлах.

Единственный авторитетный источник aspect_id — `aspect_index_additions`
в каждом патче. Ты **не читаешь аспекты из `add_aspects`** напрямую —
`add_aspects` содержит полные описания аспектов, но не является индексом.

## Построение

```
aspect_index_merged =
  concept_coverage_map.aspect_index          ← аспекты B1

  + b2_patch.aspect_index_additions          ← аспекты B2
  + b3_patch.aspect_index_additions          ← аспекты B3
  + b4_patch.aspect_index_additions          ← аспекты B4
  + b5_patch.aspect_index_additions          ← аспекты B5
  + b6_patch.aspect_index_additions          ← аспекты B6
```

После построения ты применяешь `b7_patch.aspect_status_updates`:

```yaml
status: dropped
  → аспект исключается из всех последующих проверок

status: merged
  → аспект заменяется на merge_target_aspect_id
  → все ссылки на aspect_id интерпретируются через merge target

status: active
  → без изменений

status: kept_separate
  → без изменений

status: deferred_similarity_review
  → аспект остаётся в merged index
  → помечается: similarity_status: pending
```

## Верификация полноты

После построения ты явно подсчитываешь:

```
N_B1 = количество аспектов из concept_coverage_map.aspect_index
N_B2 = количество аспектов из b2_patch.aspect_index_additions
N_B3 = количество аспектов из b3_patch.aspect_index_additions
N_B4 = количество аспектов из b4_patch.aspect_index_additions
N_B5 = количество аспектов из b5_patch.aspect_index_additions
N_B6 = количество аспектов из b6_patch.aspect_index_additions
N_dropped = количество dropped аспектов из b7_patch

ожидаемый размер = N_B1 + N_B2 + N_B3 + N_B4 + N_B5 + N_B6 - N_dropped
фактический размер = количество аспектов в aspect_index_merged
```

Если фактический размер меньше ожидаемого:

```yaml
status: BLOCK
reason: aspect_index_merge_incomplete
details:
  expected_count:
  actual_count:
  dropped_count:
```

Эти счётчики фиксируются в `artifact_meta.aspects_in_merged_index`
итогового отчёта.

Все последующие проверки C2 выполняются **только по `aspect_index_merged`**.

# STAGE 1 — Проверка трассируемости требований

Каждое требование обязано быть связано с аспектом.

Проверить наличие полей:

```yaml
requirement_id
aspect_id
traceability
```

Внутри `traceability` проверить наличие:

```yaml
traceability.aspect_id
```

## Важное правило перед фиксацией ошибки

Перед тем как зафиксировать `traceability_error` — **обязательно проверить**
что `aspect_id` из требования **действительно отсутствует** в `aspect_index_merged`.

Запрещено фиксировать traceability_error для aspect_id, который:

```
присутствует в aspect_index_merged
```

Если aspect_id присутствует в `aspect_index_merged` но отсутствует
в `requirements_index` — это `uncovered_aspect` (STAGE 1.5), не traceability_error.

## Правила проверки

1. `aspect_id` обязан существовать в `aspect_index_merged`
2. `traceability.aspect_id` обязан существовать в `aspect_index_merged`
3. `aspect_id` и `traceability.aspect_id` должны совпадать

Если нарушено:

```yaml
traceability_error:
  requirement_id:
  issue:
  aspect_id:
  verified_absent_from_merged_index: true  # обязательно подтвердить
```

Severity:

```yaml
critical
```

# STAGE 1.5 — Проверка покрытия аспектов требованиями

Ты проверяешь не поле `processed`, а **фактическое покрытие аспектов требованиями**.

Для каждого аспекта из `aspect_index_merged` вычислить:

```yaml
requirements_for_aspect =
  все требования из
    requirements_usr.yaml
    requirements_ssr.yaml
    requirements_nfr.yaml
  где requirement.aspect_id == текущий aspect_id
```

Проверка:

Если:

```yaml
aspect.mvp_impact.classification ∈ {blocker, required, supporting}
AND requirements_for_aspect.count == 0
```

фиксируется:

```yaml
uncovered_aspect:
  aspect_id:
  mvp_impact:
  severity: critical
```

Примечание: `supporting` трактуется как `required` для целей severity,
потому что C1 маппит `supporting → required` при генерации требований.
Если аспект с `supporting` не покрыт — это пропуск на уровне C1.

Если:

```yaml
aspect.mvp_impact.classification ∈ {post_mvp, technical_debt}
AND requirements_for_aspect.count == 0
```

фиксируется:

```yaml
uncovered_aspect:
  aspect_id:
  mvp_impact:
  severity: warning
```

# STAGE 2 — Проверка формата requirement_id

Формат requirement ID должен быть синхронизирован с C1.

Проверить формат:

```yaml
<type>-<aspect_id>-R<nn>
```

где:

```yaml
type = USR | SSR | NFR
nn = двухзначный порядковый номер: 01, 02, 03...
```

Примеры корректных ID:

```yaml
USR-B1-SC-001-R01
SSR-B4-AR-003-R01
NFR-B6-GV-001-R02
```

Проверить:

1. префикс соответствует типу требования
2. `aspect_id` внутри requirement_id совпадает с полем `aspect_id`
3. суффикс имеет формат `R01`, `R02`, ...
4. в рамках пары `(type, aspect_id)` нет дублирующих номеров

Если нарушено:

```yaml

  requirement_id:
  reason:
```

Severity:

```yaml
critical
```

# STAGE 5.5 — Проверка измеримости NFR

Каждый `NFR` обязан содержать измеримую метрику.

Поскольку C1 не определяет отдельное поле `measurable_metric`,
ты ищешь метрику внутри `acceptance_criteria`.

Признаки наличия измеримой метрики в `acceptance_criteria`:

```
числовой порог          (например: < 200ms, ≥ 99.9%)
диапазон значений       (например: от 10 до 100 запросов/с)
условие с измеримым результатом  (например: не более 3 retry)
правило с проверяемым исходом
```

Проверить:

1. `acceptance_criteria` содержит хотя бы один измеримый критерий
2. критерий не является пустым placeholder
3. критерий не подменяет собой описание без порога или условия

Если нарушено:

```yaml
nfr_metric_problem:
  requirement_id:
  issue: missing_metric | non_measurable_metric | placeholder_metric
```

Severity:

```yaml
critical | warning
```

Правило severity:

```yaml
missing_metric         → critical
non_measurable_metric  → warning
placeholder_metric     → warning
```

# STAGE 5.75 — Проверка согласованности NFR с snapshot

NFR-метрики не должны противоречить уже зафиксированным метрикам и экспериментальным условиям в snapshot.

Проверять против:

```yaml
snapshot.frozen_core.success_metrics_initial
snapshot.frozen_core.kill_criteria
snapshot.frozen_core.measurable_signal
```

Если обнаружен конфликт:

```yaml
nfr_snapshot_conflict:
  requirement_id:
  snapshot_metric:
  nfr_metric:
  conflict_description:
  severity: critical | warning
```

Примеры конфликтов:

* одна и та же бизнес-метрика получает разные пороги
* NFR вводит требование, делающее уже зафиксированный experiment invalid
* NFR фактически меняет смысл MVP controlled experiment

# STAGE 10 — Проверка ожидаемых типов требований по shard-first mapping

Ты используешь ту же shard-first логику, что и исправленный C1.

## Mapping expected requirement types

```yaml
core_loop     → USR + SSR + NFR
scenarios     → USR + SSR
entities      → SSR + NFR
architecture  → SSR + NFR
experiments   → SSR + NFR
operations    → SSR + NFR
governance    → SSR + NFR
marketing     → USR + SSR
```

Проверки:

1. если requirement type отсутствует там, где он ожидается как обязательный → фиксировать gap
2. если requirement type создан там, где он обычно не ожидается → фиксировать mismatch как warning, но не автоматически считать это ошибкой, если требование хорошо обосновано

Фиксации:

```yaml

  aspect_id:
  expected_type:
  severity: critical | warning
```

```yaml
requirement_type_mismatch:
  requirement_id:
  aspect_id:
  expected_types:
  actual_type:
```

Правила severity:

```yaml
отсутствует USR для core_loop / scenarios / marketing → critical
отсутствует SSR для core_loop / scenarios / entities / architecture / experiments / operations / governance / marketing → critical
отсутствует NFR для core_loop / entities / architecture / experiments / operations / governance → critical

USR для architecture / operations / governance / experiments → warning
NFR для scenarios / marketing → warning
```
