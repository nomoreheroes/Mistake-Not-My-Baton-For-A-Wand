## Схема causal_graph.db

Единственная SQLite БД, создаётся в режиме `build_review_graph`, расширяется в последующих режимах.

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = DELETE;    -- не WAL; обязательно для детерминированного файлового hash

CREATE TABLE IF NOT EXISTS graph_metadata (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
    -- Обязательные ключи: causal_graph_version, mode, covers, produced_by, run_id
    -- НЕ хранить updated_at здесь — вынесено в canonical_graph_hash-independent поле ниже
);

CREATE TABLE IF NOT EXISTS graph_timestamps (
    event TEXT PRIMARY KEY,  -- 'created_at' | 'updated_at'
    ts    TEXT NOT NULL      -- datetime('now') строка ISO-8601
    -- не входит в canonical_graph_hash, входит в db_file_hash
);

CREATE TABLE IF NOT EXISTS nodes (
    node_id        TEXT PRIMARY KEY,
    node_type      TEXT NOT NULL CHECK(node_type IN (
                     'story','process','invariant','interaction',
                     'contract','api_binding','component','spike',
                     'compound_interaction','fan_out_group','join_wait_group',
                     'arch_decision','constraint',
                     'observability_spec','deployment_spec',
                     'task','acceptance_criterion'
                   )),
    label          TEXT NOT NULL,
    attributes     TEXT,          -- JSON с нативными типами: числа, booleans, массивы, null
    source_ref     TEXT,          -- например: "process_causality_map.yaml#PROC_001"
    added_in_mode  TEXT NOT NULL CHECK(added_in_mode IN (
                     'build_review_graph','architecture_final_graph','task_trace_graph'
                   ))
);

CREATE TABLE IF NOT EXISTS edges (
    edge_id        TEXT PRIMARY KEY,
    from_node      TEXT NOT NULL REFERENCES nodes(node_id),
    to_node        TEXT NOT NULL REFERENCES nodes(node_id),
    edge_type      TEXT NOT NULL CHECK(edge_type IN (
                     'story_requires_process','process_causes_process',
                     'process_uses_invariant','process_uses_interaction',
                     'component_enforces_invariant','component_handles_interaction',
                     'interaction_has_contract','interaction_has_api_binding',
                     'spike_affects_process','spike_affects_invariant',
                     'spike_affects_interaction','spike_affects_component',
                     'compound_group_contains_interaction',
                     'fan_out_group_contains_interaction',
                     'join_wait_group_contains_interaction',
                     'precedes',
                     'blocks_until_complete',
                     'arch_decision_applies_to_component',
                     'constraint_applies_to_component',
                     'observability_spec_covers_component',
                     'deployment_spec_covers_component',
                     'task_implements_component','task_implements_contract',
                     'task_implements_api_binding',
                     'task_depends_on_task','task_has_acceptance_criterion',
                     'task_resolves_spike','task_blocked_by_spike'
                   )),
    edge_status    TEXT NOT NULL DEFAULT 'active' CHECK(edge_status IN ('active','superseded')),
    attributes     TEXT,          -- JSON
    added_in_mode  TEXT NOT NULL CHECK(added_in_mode IN (
                     'build_review_graph','architecture_final_graph','task_trace_graph'
                   ))
);

CREATE INDEX IF NOT EXISTS idx_nodes_type   ON nodes(node_type);
CREATE INDEX IF NOT EXISTS idx_edges_from   ON edges(from_node);
CREATE INDEX IF NOT EXISTS idx_edges_to     ON edges(to_node);
CREATE INDEX IF NOT EXISTS idx_edges_type   ON edges(edge_type);
CREATE INDEX IF NOT EXISTS idx_edges_status ON edges(edge_status);
```

**Порядок столбцов edges для позиционных INSERT:** `edge_id, from_node, to_node, edge_type, edge_status, attributes, added_in_mode`. `edge_status` — всегда 5-й аргумент, всегда указывать явно (`'active'`). DEFAULT применяется только при именованном INSERT с опущенным столбцом; позиционный INSERT с неверным числом аргументов вызовет `table edges has 7 columns but 6 values were supplied`. Не опускать ни один аргумент.

**Правило node_id:** `node_id` = canonical идентификатор из исходного артефакта без переименования. Примеры: `solver_runtime` (system_architecture.draft.yaml), `INV_001` (invariants_ownership.yaml), `HTTP-011` (h9_contract_spec.yaml), `API-BIND-001` (api_binding_spec.yaml), `ADR-I17-001` (architecture_decisions.yaml), `SPIKE-001` (spike_candidates.yaml), `T-001` (task_specs). Синтетические узлы, не имеющие источника-артефакта, получают генерируемый префикс: `OBS-<component_id>` (observability_spec), `DEP-<component_id>` (deployment_spec), `AC-<task_id>-<N>` (acceptance_criterion). Все остальные узлы — без добавленных префиксов. Коллизий быть не должно: canonical ID разных типов разделены по формату (INV_* vs HTTP-* vs API-BIND-* и т.д.).

**Правило JSON-атрибутов:** числа сохранять как JSON-числа, booleans как JSON-booleans, массивы как JSON-arrays, null как JSON null. Никаких строк `"true"` / `"false"` / `"null"` на месте типизированных полей. Ключи внутри `json_object()` **всегда перечислять в алфавитном порядке** (по имени ключа). Это обязательное условие детерминированности `canonical_graph_hash`: если один прогон запишет `{'blast_radius': 'x', 'status': 'open'}`, а другой — `{'status': 'open', 'blast_radius': 'x'}`, хеши не совпадут при семантически идентичном графе.

## Протокол хеширования

SQLite-файл непригоден для воспроизводимого hash: page layout, WAL-записи, порядок вставок влияют на байты файла. Используется двойная схема:

**`canonical_graph_hash`** — детерминированный hash по содержимому данных. Функция принимает **существующее соединение** (`conn`), а не открывает новое — чтобы видеть незакоммиченные вставки текущей транзакции. Использует потоковое накопление (row-by-row).

```python
import hashlib, json

def compute_canonical_hash(conn) -> str:
    """
    Вычислить canonical hash по текущему состоянию графа.
    Вызывать на том же conn, внутри транзакции, после всех INSERT и после
    записи metadata (version/mode/covers/produced_by/run_id), но ДО записи
    самого canonical_graph_hash.
    """
    h = hashlib.sha256()

    # nodes: столбцы в алфавитном порядке → row — tuple в том же порядке
    for row in conn.execute(
        "SELECT added_in_mode, attributes, label, node_id, node_type, source_ref "
        "FROM nodes ORDER BY node_id"
    ):
        h.update(json.dumps(list(row), sort_keys=True, ensure_ascii=False).encode())

    # edges: столбцы в алфавитном порядке
    for row in conn.execute(
        "SELECT added_in_mode, attributes, edge_id, edge_status, edge_type, "
        "from_node, to_node FROM edges ORDER BY edge_id"
    ):
        h.update(json.dumps(list(row), sort_keys=True, ensure_ascii=False).encode())

    # metadata: без canonical_graph_hash (ещё не записан) и без run_id (audit, не content)
    # два графа с одинаковым содержимым и разным run_id дадут одинаковый canonical_graph_hash
    for row in conn.execute(
        "SELECT key, value FROM graph_metadata "
        "WHERE key NOT IN ('canonical_graph_hash', 'run_id') ORDER BY key"
    ):
        h.update(json.dumps(list(row), sort_keys=True, ensure_ascii=False).encode())

    return h.hexdigest()
```

`canonical_graph_hash` = `compute_canonical_hash(conn)` — вызывается на той же транзакции. Столбцы запрашиваются в фиксированном алфавитном порядке, поэтому порядок полей в tuple детерминирован.

**`db_file_hash`** — sha256 от байтов файла `causal_graph.db` после VACUUM и записи `graph_timestamps`. **Non-reproducible между разными прогонами:** включает `datetime('now')` из таблицы `graph_timestamps`, поэтому два чистых прогона с идентичными входными данными дадут разный `db_file_hash`. Используется исключительно для logistics: cache-miss detection, верификация целостности скопированного файла. Никогда не использовать для сравнения содержимого между прогонами — для этого предназначен `canonical_graph_hash`.

I24 проверяет только `canonical_graph_hash` при включении в `frozen_snapshot.yaml`.

## Политика replay и транзакционная модель

### Replay-политика по режиму

| Режим | Условие replay | Действие |
|---|---|---|
| `build_review_graph` | orchestrator передаёт `replay: true` | Удалить файл `causal_graph.db` целиком; начать заново |
| `build_review_graph` | `causal_graph.db` существует без `replay: true` | **FAIL**: сообщить оркестратору, не перезаписывать |
| `architecture_final_graph` | orchestrator передаёт `replay: true` | Восстановить файл из `causal_graph.db.v1.bak` (см. ниже); начать заново |
| `architecture_final_graph` | `graph_metadata.causal_graph_version = '2'` без `replay: true` | **FAIL** |
| `task_trace_graph` | orchestrator передаёт `replay: true` | Восстановить файл из `causal_graph.db.v2.bak`; начать заново |
| `task_trace_graph` | `replay: true` И `causal_graph.db.v2.bak` отсутствует | **FAIL**: `v2.bak not found — re-run architecture_final_graph first` |
| `task_trace_graph` | `graph_metadata.causal_graph_version = 'final'` без `replay: true` | **FAIL** |

### Транзакционная модель

Каждый режим выполняется атомарно:

```
BEGIN IMMEDIATE;
  [1] Вставить все узлы и рёбра режима
  [2] Выполнить self-check (без изменений)
  [3] Если self-check провалился → ROLLBACK; записать i7_self_check_failure.yaml; обновить replay_log; STOP
  [4] Записать metadata (version, mode, covers, produced_by, run_id) — БЕЗ canonical_graph_hash
  [5] Вычислить canonical_graph_hash = compute_canonical_hash(conn)
      — на той же транзакции, видит все вставки шагов [1] и [4]
  [6] INSERT OR REPLACE INTO graph_metadata(key, value) VALUES('canonical_graph_hash', <hash>)
COMMIT;

-- на той же conn (никаких новых соединений):
[7] Записать graph_timestamps (created_at / updated_at) — INSERT OR REPLACE; затем conn.commit()
    ВАЖНО: Python sqlite3 открывает implicit transaction при DML после COMMIT — без явного
    conn.commit() перед VACUUM получим "cannot VACUUM from within a transaction"
[8] PRAGMA wal_checkpoint(TRUNCATE); VACUUM; conn.close()
[9] Вычислить db_file_hash от файла — файл стабилен (timestamp уже внутри после VACUUM)
[10] Создать бэкап: v1.bak (build_review_graph) или v2.bak (architecture_final_graph)
[11] Обновить i_layer_run.yaml
```

**Ключевые порядковые инварианты:**
- Metadata (version/mode/covers) записывается на шаге **[4]** внутри транзакции, чтобы попасть в canonical hash
- `canonical_graph_hash` вычисляется на шаге **[5]** — после всех INSERT и после [4], на той же `conn`; функция исключает ключ `canonical_graph_hash` из запроса
- `graph_timestamps` пишется на шаге **[7]** — на той же открытой `conn`, после COMMIT, в autocommit-режиме; никакого нового соединения
- `VACUUM` на шаге **[8]** компактирует всё включая timestamp в единый стабильный файл; после `conn.close()` файловых дескрипторов нет
- `db_file_hash` вычисляется на шаге **[9]** — на закрытом файле после VACUUM; timestamp включён, файл не изменится
- Бэкап создаётся на шаге **[10]** — после `db_file_hash`, до `i_layer_run.yaml`

**Критично:** `graph_metadata.causal_graph_version` и `mode` обновляются **только после успешного self-check** внутри транзакции. Если агент упал между шагами 1 и 5 — `ROLLBACK` откатит всё; следующий запуск получит корректное предыдущее состояние.

### Failure-signal протокол

I7 — downstream-сборщик графа; он не исправляет upstream-артефакты и не выбирает архитектурные решения. Если self-check любого режима провалился, I7 обязан:

1. Выполнить `ROLLBACK`.
2. Убедиться, что `causal_graph.db` / `.bak` текущего режима не созданы или не заменены.
3. Записать диагностический артефакт:

```yaml
i7_self_check_failure:
  schema_version: "1.0"
  source_agent: I7
  run_id: <из i_layer_run.yaml>
  mode: build_review_graph | architecture_final_graph | task_trace_graph
  failure_type: self_check_failed
  blocking: true
  artifact_created: false
  failed_checks:
    - check_id: process_to_invariant
      target_agents: [I3, I4]
      affected_elements:
        - node_id: <PROC_*>
          node_type: process
          name: <process.name>
          source_ref: process_causality_map.yaml#<PROC_*>
          missing:
            - process_uses_invariant
            - explicit_no_invariant_reason
          allowed_remediation:
            - I3 adds explicit_no_invariant_reason when process is navigation-only, orchestration-proxy, or read-only aggregation
            - I4 maps process to an existing or newly justified invariant
  required_replay:
    - target_agent: <I3|I4|I5|I6|I20|I21|I23>
      reason: <why this producer owns the fix>
    - target_agent: I6
      reason: rerun architecture synthesis after foundational I3/I4/I5 changes
    - target_agent: I7
      mode: <same mode that failed>
      replay: true
```

4. Записать `i_layer_run.yaml#replay_log`:

```yaml
replay_log:
  - replay_id: I7-SELF-CHECK-<N>
    source_agent: I7
    signal_type: causal_graph_self_check_failure
    target_agent: external_pipeline_orchestrator
    reason: <short summary>
    affected_artifacts:
      - TEST WORKFLOW/9. I. Architecture & Task Graph RS/i7_self_check_failure.yaml
    status: blocked_pending_upstream_replay
```

5. Установить `current_stage: upstream_replay_required`.

**Routing table для `failed_checks`:**

| failed_check | target_agents | Почему |
|---|---|---|
| `story_requires_process` | I3 | story→process принадлежит process map |
| `process_to_invariant` | I3, I4 | I3 может дать допустимое `explicit_no_invariant_reason`; I4 может добавить process→invariant |

| `task_traceability_gap` | I20, I21, I23 | task graph/spec/QA создают task provenance и acceptance criteria |

`i7_self_check_failure.yaml` — не то же самое, что `upstream_signal.yaml` I14–I19→I6. Это структурный failure-сигнал к producer-агентам. Оркестратор маршрутизирует его к указанным `target_agents`, затем запускает обязательный downstream replay: I6 (если менялись I3/I4/I5/I6 outputs) → I7 с `replay: true`.

| Бэкап | Создаётся в | Используется для replay |
|---|---|---|
| `causal_graph.db.v1.bak` | build_review_graph, шаг [D] | architecture_final_graph |
| `causal_graph.db.v2.bak` | architecture_final_graph, шаг [C] | task_trace_graph |

Файловый restore детерминирован только для **стартового состояния** replay: физическое состояние страниц `.bak` идентично точке создания бэкапа. Итоговый `db_file_hash` после повторного прогона режима может отличаться из-за новых значений `graph_timestamps`. Содержательное сравнение выполняется только через `canonical_graph_hash`. DELETE FROM не используется: после DELETE страницы уходят в freelist и при повторных INSERT размещаются иначе — `db_file_hash` стартового состояния тоже будет нестабильным.

```python

shutil.copy2('causal_graph.db.vN.bak', 'causal_graph.db')
```

**Lineage policy для `causal_graph.db` (обязательно для всех режимов I7).**

Один физический файл `causal_graph.db` публикуется в трёх логических artifact-family:

| mode | artifact_family | legacy artifact_id |
|---|---|---|
| `build_review_graph` | `I7_BUILD_REVIEW_GRAPH` | `ARTIFACT-I7-V1` |
| `architecture_final_graph` | `I7_ARCHITECTURE_FINAL_GRAPH` | `ARTIFACT-I7-V2` |
| `task_trace_graph` | `I7_TASK_TRACE_GRAPH` | `ARTIFACT-I7-FINAL` |

`supersedes` разрешён только внутри той же `artifact_family` и того же `mode`. Cross-mode связь фиксируется полями `derived_from`, `base_graph`, `invalidates`, `requires_rerun`, но **не** `supersedes`. Пример: replay `build_review_graph` после уже опубликованного `architecture_final_graph` может записать `invalidates: [ARTIFACT-I7-V2]` и `requires_rerun: [I7_architecture_final_graph, I20, I21, I22, I23]`, но не может писать `supersedes: ARTIFACT-I7-V2`.

Любой consumer, которому нужен конкретный режим, выбирает head по `artifact_family`/`mode`, а не глобально по `path=causal_graph.db`. Дополнительно consumer обязан сверить `db_file_hash` выбранного artifact с фактическим hash файла на диске; если hash не совпал, физический файл принадлежит другому режиму или устарел, и текущий gate должен блокироваться с требованием rerun нужного режима I7.

## Навигация по графу (для reviewers и J-слоя)

Граф — ориентированный, но traversal для трассировки частично идёт против направления рёбер. Это нормально — используется `JOIN` в обоих направлениях.

### Трассировка task → story (J-layer, единый UNION-запрос)

Три пути трассировки объединены в один запрос. Путь A: task → component → invariant → process → story (code.domain_logic). Путь B: task → contract/api_binding → interaction → process → story (code.contract, infrastructure). Путь C: task → spike → process → story (research-задачи без прямого component/contract).

```sql
-- Путь A: task → component → invariant → process → story
SELECT DISTINCT s.node_id AS story_id, s.label AS story_label
FROM nodes s
JOIN edges se ON se.from_node = s.node_id
             AND se.edge_type = 'story_requires_process'
             AND se.edge_status = 'active'
JOIN edges pi ON pi.from_node = se.to_node
             AND pi.edge_type = 'process_uses_invariant'
             AND pi.edge_status = 'active'
JOIN edges ci ON ci.to_node   = pi.to_node
             AND ci.edge_type = 'component_enforces_invariant'
             AND ci.edge_status = 'active'
JOIN edges tc ON tc.from_node = :task_id
             AND tc.edge_type = 'task_implements_component'
             AND tc.to_node   = ci.from_node
WHERE s.node_type = 'story'

UNION

-- Путь B: task → contract/api_binding → interaction → process → story
SELECT DISTINCT s.node_id AS story_id, s.label AS story_label
FROM nodes s
JOIN edges se ON se.from_node = s.node_id
             AND se.edge_type = 'story_requires_process'
             AND se.edge_status = 'active'
JOIN edges pi ON pi.from_node = se.to_node
             AND pi.edge_type = 'process_uses_interaction'
             AND pi.edge_status = 'active'
JOIN edges ic ON ic.from_node = pi.to_node
             AND ic.edge_type IN ('interaction_has_contract', 'interaction_has_api_binding')
             AND ic.edge_status = 'active'
JOIN edges tc ON tc.from_node = :task_id
             AND tc.edge_type IN ('task_implements_contract', 'task_implements_api_binding')
             AND tc.to_node   = ic.to_node
WHERE s.node_type = 'story'

UNION

-- Путь C: task → spike → process → story (research без прямого component/contract)
SELECT DISTINCT s.node_id AS story_id, s.label AS story_label
FROM nodes s
JOIN edges se ON se.from_node = s.node_id
             AND se.edge_type = 'story_requires_process'
             AND se.edge_status = 'active'
JOIN edges sp ON sp.to_node   = se.to_node
             AND sp.edge_type = 'spike_affects_process'
             AND sp.edge_status = 'active'
JOIN edges ts ON ts.from_node = :task_id
             AND ts.edge_type = 'task_resolves_spike'
             AND ts.to_node   = sp.from_node
WHERE s.node_type = 'story';
```

Если запрос вернул 0 строк — применять type-aware trace contract:

- `qa` трассируется через валидированные I23 поля `covered_task_ids` / `covered_invariant_ids` и собственные acceptance criteria; прямой SQL-path до story не обязателен;
- `human_action` трассируется через валидированный I23 external-action contract (`external_system`, `action_type`, `actor_role`, `evidence_required`) и `artifact_refs`; прямой SQL-path до story не обязателен;
- для всех остальных типов отсутствие строки — `task_traceability_gap`.

Эти исключения не освобождают `qa`/`human_action` от создания task-узла и acceptance criteria. Они существуют потому, что канонический словарь I7 не содержит искусственных рёбер `qa→story` или `human_action→story`; запрещено подменять их ложным `task_implements_component`.

### Найти все компоненты, реализующие инвариант (reviewer)

```sql
SELECT c.node_id, c.label
FROM nodes c
JOIN edges e ON e.from_node = c.node_id
            AND e.edge_type = 'component_enforces_invariant'
            AND e.to_node = :invariant_id
            AND e.edge_status = 'active'
WHERE c.node_type = 'component';
```

### Найти все задачи для компонента (J-layer)

```sql
SELECT t.node_id, t.label, t.attributes
FROM nodes t
JOIN edges e ON e.from_node = t.node_id
            AND e.edge_type = 'task_implements_component'
            AND e.to_node = :component_id
WHERE t.node_type = 'task';
```

**Заметка для J-layer:** всегда фильтровать `edge_status = 'active'`. Superseded-рёбра — это исторический аудит; J не должен их читать в рабочих запросах.

### Шаг 2 — Загрузить story-узлы из prd.index.yaml

`prd.index.yaml` row-based: один `story_id` может появляться в нескольких строках (по одной на `requirement_id`). Перед INSERT агрегировать по `story_id`:

```python
from collections import defaultdict

stories = defaultdict(lambda: {
    'label': '',
    'requirement_ids': [],
    'mvp_priority': None,
    'story_type': None,
    'aspects': [],
})
for row in prd_index_rows:
    sid = row['story_id']
    stories[sid]['label'] = row.get('story_name', sid)
    stories[sid]['mvp_priority'] = row.get('mvp_priority')
    stories[sid]['story_type'] = row.get('story_type')
    if row.get('requirement_id') and row['requirement_id'] not in stories[sid]['requirement_ids']:
        stories[sid]['requirement_ids'].append(row['requirement_id'])
    if row.get('aspect') and row['aspect'] not in stories[sid]['aspects']:
        stories[sid]['aspects'].append(row['aspect'])
```

Затем INSERT для каждого уникального `story_id`:

### Ограничение идемпотентности

В основной транзакции построения (`BEGIN IMMEDIATE; ... COMMIT`) допустимы **только** операции `INSERT` для узлов типа `task` и `acceptance_criterion`, и `INSERT` рёбер от/к ним. **Категорически запрещено:** UPDATE, DELETE, пересоздание узлов типов `component`, `invariant`, `interaction`, `arch_decision`, `constraint`, `observability_spec`, `deployment_spec`. Любое изменение существующих узлов делает `canonical_graph_hash` недетерминированным — I24 не сможет верифицировать граф при повторном прогоне.

**Replay:** восстановить файл из `causal_graph.db.v2.bak` (аналогично architecture_final_graph ← v1.bak). DELETE FROM не используется — физическое состояние страниц после DELETE отличается от чистого прогона, что делает `db_file_hash` нестабильным. Файловый restore детерминирован для **стартового состояния** replay; `db_file_hash` итогового файла после повторного прогона будет отличаться из-за новых значений `graph_timestamps` — это нормально. Содержательное сравнение выполняется только через `canonical_graph_hash`.

```sql
-- Объединённая трассировка: три пути task → story
-- Путь A: task → component → invariant → process → story
SELECT DISTINCT s.node_id AS story_id FROM nodes s
JOIN edges se ON se.from_node = s.node_id AND se.edge_type = 'story_requires_process' AND se.edge_status = 'active'
JOIN edges pi ON pi.from_node = se.to_node AND pi.edge_type = 'process_uses_invariant'   AND pi.edge_status = 'active'
JOIN edges ci ON ci.to_node = pi.to_node   AND ci.edge_type = 'component_enforces_invariant' AND ci.edge_status = 'active'
JOIN edges tc ON tc.from_node = :task_id   AND tc.edge_type = 'task_implements_component' AND tc.to_node = ci.from_node
WHERE s.node_type = 'story'
UNION
-- Путь B: task → contract/api_binding → interaction → process → story
SELECT DISTINCT s.node_id FROM nodes s
JOIN edges se ON se.from_node = s.node_id AND se.edge_type = 'story_requires_process' AND se.edge_status = 'active'
JOIN edges pi ON pi.from_node = se.to_node AND pi.edge_type = 'process_uses_interaction' AND pi.edge_status = 'active'
JOIN edges ic ON ic.from_node = pi.to_node AND ic.edge_type IN ('interaction_has_contract','interaction_has_api_binding') AND ic.edge_status = 'active'
JOIN edges tc ON tc.from_node = :task_id   AND tc.edge_type IN ('task_implements_contract','task_implements_api_binding') AND tc.to_node = ic.to_node
WHERE s.node_type = 'story'
UNION
-- Путь C: task → spike → process → story (research-задачи без прямого component/contract)
SELECT DISTINCT s.node_id FROM nodes s
JOIN edges se ON se.from_node = s.node_id AND se.edge_type = 'story_requires_process' AND se.edge_status = 'active'
JOIN edges sp ON sp.to_node   = se.to_node AND sp.edge_type = 'spike_affects_process'   AND sp.edge_status = 'active'
JOIN edges ts ON ts.from_node = :task_id   AND ts.edge_type = 'task_resolves_spike'     AND ts.to_node = sp.from_node
WHERE s.node_type = 'story';
```

`causal_graph.db` (v2) — I20 использует для декомпозиции задач: читает все `component` узлы, их `arch_decision` связи, `observability_spec` и `deployment_spec` точки. Граф даёт готовый контекст без необходимости читать все исходные артефакты повторно.

**task_trace_graph → I24 (Gatekeeper):**

`causal_graph.db` (final) — I24 верифицирует `canonical_graph_hash` из `graph_metadata` против записанного в `i_layer_run.yaml` перед включением в `frozen_snapshot.yaml`. При верификации I24 **обязан использовать ту же функцию `compute_canonical_hash`** с теми же исключениями: `WHERE key NOT IN ('canonical_graph_hash', 'run_id')`. Отклонение от этих исключений (например, включение `run_id`) даст другой hash и ложно заблокирует граф. J-слой использует граф для трассировки и навигации (см. раздел «Навигация по графу»).
