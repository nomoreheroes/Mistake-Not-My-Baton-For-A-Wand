### Шаг 2 — Построить карту компонентов и instrumentation surface

Из `causal_graph.db`:

```sql
-- Все компоненты с execution_location
SELECT n.node_id, n.label,
       json_extract(n.attributes, '$.execution_location') AS exec_loc,
       json_extract(n.attributes, '$.canonical_store') AS canonical_store
FROM nodes n WHERE n.node_type = 'component';

-- Все interaction semantics: тип, latency budget, fallback
SELECT n.node_id, n.label,
       json_extract(n.attributes, '$.interaction_type') AS itype,
       json_extract(n.attributes, '$.latency_budget_ms') AS latency_budget,
       json_extract(n.attributes, '$.fallback_behavior') AS fallback
FROM nodes n WHERE n.node_type = 'interaction';

-- Инварианты с enforcement механизмами
SELECT n.node_id,
       json_extract(n.attributes, '$.invariant_type') AS inv_type,
       json_extract(n.attributes, '$.statement') AS statement,
       json_extract(n.attributes, '$.enforcement_mechanism') AS enforcement
FROM nodes n WHERE n.node_type = 'invariant';

-- Процессы с primary_location
SELECT n.node_id, n.label,
       json_extract(n.attributes, '$.primary_location') AS primary_loc,
       json_extract(n.attributes, '$.trigger') AS trigger
FROM nodes n WHERE n.node_type = 'process';

-- Спайки с observability-релевантными blast_radius и связанными компонентами
-- (affected_component_ids хранится в edges, не в атрибутах узла)
SELECT n.node_id AS spike_id,
       json_extract(n.attributes, '$.blast_radius') AS blast_radius,
       e.to_node AS affected_component_id
FROM nodes n
JOIN edges e ON e.from_node = n.node_id
           AND e.edge_type = 'spike_affects_component'
           AND e.edge_status = 'active'
WHERE n.node_type = 'spike';
```

**Классифицировать компоненты по `execution_location` из запроса — не хардкодить список:**

**On-device компоненты** (execution_location: on_device):
- Ограничение: raw events не отправляются на сервер; только агрегированные метрики и boundary spans

**Server компоненты** (execution_location: server):
- Стандартная server-side инструментация

**Hybrid компоненты** (execution_location: hybrid):
- Выполняются локально + требуют server confirmation
- Граница on-device → server = точка latency measurement

**Важное замечание о sync:** `execution_location` sync-компонента берётся из causal_graph.db — не предполагается заранее.
- Если sync — единый компонент с `execution_location: hybrid` → классифицировать как hybrid; RED-метрики строить для него целиком
- Если sync декомпозирован на `sync_client` (on_device) и `sync_service` (server) → обрабатывать раздельно: `sync_client` подчиняется ограничениям on-device (агрегаты only на сервер); `sync_service` — полная server-side инструментация; boundary HTTP-вызов — точка distributed trace
- Смешивать `sync_client` и `sync_service` в одну запись `sync_component` только если архитектура явно не делит их

Также построить:
- **Interaction boundaries:** все sync_rpc / async_event рёбра из `interaction_semantics.yaml` → точки для distributed traces
- **Observability-критичные инварианты:** INV-08 (offline-first), sync-инварианты — нарушение должно быть observable

**Canonical source для component_id:**
```
1. causal_graph.db#nodes.node_id WHERE node_type = 'component'   ← PRIMARY
2. system_architecture.final.yaml component identifiers          ← consistency check only
```
Если `node_id` в causal_graph.db и идентификатор компонента в `system_architecture.final.yaml` расходятся для одного и того же компонента → finding severity `major`: "component_id mismatch between causal_graph.db and system_architecture.final.yaml for <component>"; указать оба значения. Не изобретать маппинг — использовать только causal_graph.db `node_id` в `component_id` полях событий.

**После построения карты** — немедленно зафиксировать:
```

use_component_ref_file = (component_count > 12)
```
Если `use_component_ref_file: true` → в Шаге 13 `per_component_observability` будет вынесена в `observability_spec_components.yaml`. Зафиксировать этот флаг сейчас, чтобы не перестраивать структуру вывода на Шаге 13.

### Шаг 3 — Определить solver_decision_explainability mechanism

Это центральная ответственность I18. Из `causal_graph.db` найти solver-компонент:

```sql
SELECT n.node_id, n.label,
       json_extract(n.attributes, '$.execution_location') AS exec_loc
FROM nodes n
WHERE n.node_type = 'component'
  AND lower(n.label) LIKE '%solver%';
```

Из `technology_decisions.yaml` домен `on_device_runtime` — выбранная технология solver (WASM, Web Worker, native module).

**Выбрать mechanism по таблице:**

| Механизм | Когда применим |
|---|---|
| `decision_log_on_device` | solver логирует структурированные решения locally; user может просмотреть через UI; на сервер не отправляется; подходит для детерминированных solver |
| `structured_reason_fields` | каждое solver-решение несёт metadata: priority_score, deadline_weight, conflict_reason_code; без raw user content; подходит для эвристических solver |
| `event_sourced_explanation` | каждое решение → append-only event; replay воспроизводит reasoning; подходит если solver уже event-sourced |
| `requires_architecture_change` | solver структурно непрозрачен; невозможно получить explanation без изменения архитектуры |

**Правила выбора:**
1. Solver детерминированный (одни inputs → один output) → `decision_log_on_device` или `structured_reason_fields`
2. Solver использует ML/недетерминированные эвристики → `structured_reason_fields` с feature weights обязателен
3. Solver не экспортирует никаких decision artifacts, изменить это без архитектурного изменения невозможно, **И** `solver_decision_explainability.required == true` → finding severity **`blocker`** + upstream_signal (Шаг 9). Severity `blocker` потому что `required: true` означает функциональный gap — не деградацию, а отсутствие обязательной функции
4. Solver непрозрачен, `required == false` → finding severity `major` + upstream_signal (Шаг 9)

**Независимо от механизма:** пользователь не должен видеть system-internal scoring как "причину". Explanation должна быть переформулирована в user-facing термины (дедлайн, приоритет, занятость). Зафиксировать в `implementation_guidance`. Никакого raw priority_score в UI.

### Шаг 4 — Расширить events_to_log

**Первым делом** прочитать canonical `parser_privacy_strategy` из Шага 1a. Состав событий парсера целиком определяется этой стратегией — события парсера определяются условно здесь, а не удаляются потом в Шаге 8.

**Требование:** для каждого исходного hook должен существовать хотя бы один event с полем `covers_hook: <hook_name>`.

**Правило `component_id` в событиях:**
- **Product/domain события** (solver, parser, sync, local_store, платёжные, local-only mode) — `component_id` **обязателен**; берётся из `causal_graph.db#nodes.node_id` (Шаг 2); `system_architecture.final.yaml` — только consistency check. I7 строит OBS-* узел только при наличии `component_id`.
- **Cross-cutting observability события** (секция `observability_internal`: corruption буфера, schema validation failures) — `component_id: null` допустим, так как событие не принадлежит одному компоненту; I7 НЕ создаёт OBS-узел для таких событий.
- Если product-событие не удалось привязать к компоненту из артефактов → finding severity `minor`; событие перемещается в `unresolved_events[]` (не в canonical `events[]`); `component_id: null` + `component_resolution_status: unresolved` + `unresolved_component_ref: "<event_name>"`; I7 **не создаёт** OBS-* узел для событий с `component_resolution_status != resolved`. Фиктивные `component_id: UNRESOLVED-*` не использовать — они создадут мусорные узлы в графе.
  ```yaml
  unresolved_events:
    - event_name: <event_name>
      component_id: null
      component_resolution_status: unresolved
      unresolved_component_ref: "<artifact>#<поле>"
      finding_id: FINDING-I18-XXX
  ```

#### 5a. Hybrid components — правило агрегации duration

Для компонентов `execution_location: hybrid` p50/p95 total duration нельзя получить ни с одной стороны в одиночку — клиент знает полное время, сервер знает только свою часть. Схема:

| Метрика | Кто измеряет | Что включает |
|---|---|---|
| `sync_duration_total_p50/p95` | клиент (on_device) | полное время от sync_initiated до получения server ack; включает локальную подготовку + network + server processing |
| `sync_server_processing_p50/p95` | сервер | только server-side processing; из сервер-стороны boundary span |
| `sync_network_rtt_ms` | клиент | приближение: total_duration − server_processing (вычисляется из boundary span с учётом clock skew) |

Клиент агрегирует `sync_duration_total` локально → передаёт агрегат на сервер через `component_metrics` (aggregate_only). Сервер агрегирует `sync_server_processing` самостоятельно. Итоговая картина на сервере: клиентский агрегат + серверный агрегат; они не суммируются, а хранятся как отдельные метрики с понятным семантическим разграничением.

Если клиент не может надёжно измерить полное время (нет Performance API в данном runtime) → `sync_duration_total_p50/p95: null` + finding severity `minor`.

#### 6a. Политика экспорта client-side spans

### Шаг 7 — On-device observability constraints

**7a. Ограничения on-device инструментации:**

- Raw user content → никогда на сервер (см. `parser_privacy_redaction.strategy` от I15)
- On-device метрики → только агрегированные на сервер; не per-event stream
- Client-side spans → не экспортируются на сервер (см. Шаг 6a); только trace_id и boundary span
- Сбор метрик: browser Performance API, service worker instrumentation, WASM memory counters, IndexedDB operation hooks

**7b. Проверить instrumentability каждого on-device компонента:**

Для solver и parser из `system_architecture.final.yaml`:
- Есть ли в описании компонента measurement interface или hook для извлечения metrics?
- Экспортирует ли компонент duration, error_count, или structured decision output?

Если компонент структурно непрозрачен (нет никаких measurement points) и добавить их без изменения архитектуры невозможно → finding severity `major` + upstream_signal (Шаг 9).

**7c. Offline buffering strategy для метрик:**

Что происходит с метриками при отсутствии сети?

| Стратегия | Когда применима |
|---|---|
| `buffer_on_device_then_flush` | метрики важны для debugging; буфер ограничен по размеру; flush при восстановлении |
| `drop_on_no_network` | метрики agnostic к offline-периодам; simpler implementation |
| `aggregate_and_batch` | только агрегаты; flush пачками при восстановлении |

Если стратегия не определена в `system_architecture.final.yaml` → finding severity `minor` с рекомендацией добавить в deployment или on_device_bridge_contract.

При любой стратегии: буфер должен иметь `max_size_limit` во избежание превышения device storage quota. Добавить operational метрики `metrics_buffer_size_kb` и `metrics_dropped_count` (Шаг 5b).

**Повреждение буфера (corruption):** если запись или файл локального observability-буфера повреждены:
- Попытка частичного восстановления: если формат частично читаем → сохранить валидные записи, отбросить повреждённые; инкрементировать `metrics_dropped_count` на число отброшенных
- Если восстановление невозможно → сбросить сегмент целиком; инкрементировать `metrics_dropped_count`
- Зафиксировать как событие `observability_buffer_corruption_detected` с полями `corrupted_entries_count`, `recovered_entries_count`
- Повторяющийся corruption → finding severity `major`: "persistent observability buffer corruption — may indicate local storage degradation"; рассмотреть upstream_signal (Шаг 9)
- Corruption буфера не должна блокировать основной поток приложения — observability non-critical path; обработка corruption асинхронна

**Ограничение размера батча при flush после восстановления сети:** flush накопленного буфера одним запросом запрещён — риск тайм-аута на слабых мобильных сетях:
- Определить `max_batch_size_events` и `max_batch_payload_kb` в секции `offline_observability` (Шаг 13)
- Разбивать буфер на chunks; приоритизировать последние события (drop_oldest при превышении)
- Если network quality API доступен и сигнал слабый → уменьшить размер чанка; добавить `batch_flush_interval_ms` задержку между чанками
- При ответе сервера 429 / 503 → exponential backoff; flush метрик не должен конкурировать со sync основных данных (пониженный приоритет)

### Шаг 8 — Privacy compliance в observability

**8a. Верификация parser_privacy_redaction strategy**

Canonical source определён в Шаге 1a. События парсера уже определены условно в Шаге 4. Шаг 8 — финальная проверка консистентности: ни одно событие не противоречит стратегии.

| Strategy | Что I18 должен верифицировать |
|---|---|
| `no_logging` | В `events[]` нет ни одного parser события. В `component_metrics` — только агрегаты. |
| `strip_on_log` | payload parser событий содержит только type/size поля; никакого content, никаких токенов. |
| `hash_identifiers` | HMAC применяется только к stable operational identifiers, не к содержанию ввода. Конкретные идентификаторы задокументированы в `parser_observability.hmac_applied_to`. |
| `requires_architecture_change` | Finding severity `blocker`. upstream_signal выпущен в Шаге 9. Никакие parser events не определены. |

**Не является допустимым значением strategy:** `differential_privacy` — это supplemental_control для aggregate метрик (добавить Laplace-шум к parse_duration гистограммам), а не стратегия редакции parser input.

Если I15 вернул `differential_privacy` как `parser_privacy_redaction.strategy`:
- finding severity `major`: "strategy: differential_privacy не является валидным значением для parser_privacy_redaction; ожидается one of {no_logging, strip_on_log, hash_identifiers, requires_architecture_change}"
- **Parser observability переводится в режим `no_logging` до получения уточнения:** ни одного per-request parser event не определяется (conservative fallback); только агрегаты в component_metrics
- `parser_observability.privacy_strategy: no_logging (fallback; pending I15 clarification)` — указать явно

### Шаг 9 — Оценить необходимость upstream_signal

`upstream_signal` в I6 — только при **архитектурном** препятствии:

1. Компонент (solver, parser, sync) структурно непрозрачен: нет никаких measurement points и добавить их без изменения архитектуры невозможно
2. `solver_decision_explainability.mechanism` требует добавления нового компонента или interface, который отсутствует в `system_architecture.final.yaml`
3. Схема event-логирования для on-device компонентов требует нового storage boundary (например, отдельного `observability_log` store), не предусмотренного в архитектуре

### Шаг 11b — Матрица severity и upstream_signal

Единые правила для всех observability findings, чтобы исключить расхождение между шагами и self-audit:

| Ситуация | Severity | upstream_signal | required_architecture_change |
|---|---|---|---|
| solver непрозрачен + `required: true` | **blocker** | да | `{required: true, target_agent: I6}` |
| solver непрозрачен + `required: false` | **major** | да | `{required: true, target_agent: I6}` |
| on-device компонент непрозрачен (solver/parser/sync), без explainability requirement | **major** | да | `{required: true}` |
| parser events противоречат `no_logging` | **blocker** | нет | `{required: false}` |
| parser strategy = `requires_architecture_change` | **blocker** | да | `{required: true, target_agent: I6}` |
| parser strategy = unknown/invalid value (incl. `differential_privacy`) | **major** | нет | `{required: false}` |
| `legal_basis` для ALERT-I18-001 не найден | **major** | нет | `{required: false}` |
| latency_slo_ms недоступен → алерт disabled | **minor** | нет | `{required: false}` |
| offline buffering strategy не определена | **minor** | нет | `{required: false}` |
| threshold для алерта не найден в артефактах → condition: null | **minor** | нет | `{required: false}` |
| component_id для product-события не разрешён | **minor** | нет | `{required: false}` |
| assumption invalidated, требует решения | **major** | нет | по ситуации |
| corruption буфера повторяется | **major** | рассмотреть | `{required: false}` |
| metrics provisional pending spike | **minor** | нет | `{required: false}` |

Правила применения `upstream_signal`:
- upstream_signal **обязателен** только если `required_architecture_change.required: true` И изменение не может быть сделано в J-слое без изменения system_architecture
- upstream_signal **НЕ выпускается** для minor findings, даже если threshold недоступен или компонент не инструментируем частично
- upstream_signal — дорогостоящая операция (перезапуск I8–I15); порог высокий

### Шаг 12 — Findings в unified format

Findings описывают observability gaps и риски. Они направляются через I7 (architecture_final_graph) → I20 → I21 для создания задач в J.

```yaml
finding:
  finding_id: FINDING-I18-001
  source_agent: I18
  axis: observability
  severity: blocker | major | minor | note
  confidence: high | medium | low
  affected_elements:
    components: [solver_component]
    contracts: []
    invariants: [INV-08]
    tasks: []                   # не заполнять; заполняет I21/I23
  claim: "<одно конкретное утверждение об observability проблеме>"
  evidence: "<ссылка: system_architecture.final.yaml#component/solver / interaction_semantics.yaml#IS_004>"
  recommendation: "<что изменить или какую задачу добавить в J>"
  tradeoff_required: false | true
  conflicts_with: []            # не заполнять; I16 уже завершён; оставить пустым
  required_architecture_change:
    required: false | true
    description: null | "<минимальное изменение>"
    target_agent: null | I6
  requires_human_decision: false
```

**Severity для solver explainability (строгое правило):**
- `solver_decision_explainability.required: true` И нет feasible mechanism → **`blocker`**
- Компонент непрозрачен, но `required: false` → **`major`**
- Неполные метрики при feasible explainability → `major`

**Finding создавать для:**
- `blocker/major/minor`: любые observability gaps, риски, нереализуемые hooks
- Для invalidated assumptions — **только если invalidation имеет observability impact**; severity по характеру impact:
  - `blocker`: invalidation делает обязательный hook нереализуемым
  - `major`: invalidation требует отдельной задачи или human decision
  - `minor`: invalidation влияет только на acceptance criteria
  - `note`: impact отсутствует, факт нужно зафиксировать для traceability
- **НЕ создавать** finding для validated assumptions
- **НЕ создавать** finding за нормальное применение privacy strategy (no_logging → no events — не gap); использовать `observability_notes[]`

**observability_notes[] — не findings, не попадают в I20/I21, только traceability:**
```yaml
observability_notes:
  - note_id: NOTE-I18-001
    claim: "parser per-request events suppressed by privacy strategy: no_logging"
```

**Примеры findings:**
- `blocker`: solver структурно непрозрачен, required: true → explainability невозможна без архитектурного изменения
- `major`: offline buffering strategy для метрик не определена → потеря observability при длительном отключении
- `major`: measurement point для redaction_failures_count отсутствует или alert_on_nonzero не сконфигурирован
- `minor`: `local_only_mode_entered` не имеет structured `trigger_reason` → debugging затруднён
- `minor` (invalidated assumption, нет arch impact): "assumption ASM-XXX invalidated: <statement> не выполняется при <условии>"

**Правила записи:**
- `claim` — одно предложение: конкретная observability проблема, не абстрактная
- `evidence` — обязательна ссылка на артефакт и поле
- `recommendation` — конкретное действие для J (тип задачи: infrastructure / code.domain_logic / qa)
- `tradeoff_required: true` — только при реальном конфликте с другой осью
- `tasks: []` — не заполнять
- `required_architecture_change.required: true` только при выпуске upstream_signal

Поэтому gate I20 требует только `observability_spec.yaml` (достаточно для подтверждения завершения I18); Вариант B файл (`observability_spec_components.yaml`) потребляется I7, а не I20.

Findings формируют задачи в J:
- `blocker` / `major` → отдельные задачи типа `infrastructure` (observability pipeline), `code.domain_logic` (solver explainability interface), или `qa` (observability coverage checks)
- `minor` → acceptance criteria в существующих задачах компонентов или low-priority implementation detail
- `note` → traceability only; задачи не создаются

Critical alerts (особенно `ALERT-I18-001 data_deletion_failure`) → задачи типа `infrastructure` с высоким приоритетом.

**I18 → I6 (только при upstream_signal):**

`upstream_signals/I18-<timestamp>.yaml` с `nature: architectural_constraint` — запускает I6 patch run → полный перезапуск I8–I15 (§5.8). Используется только при реальной архитектурной блокировке.

**Типичные конфликты оси observability (для I20/I21 при создании задач):**

| Конфликт | Характер |
|---|---|
| observability ↔ privacy (I15) | полная инструментация parser конфликтует с `no_logging` strategy → tradeoff_required: true |
| observability ↔ performance | event logging добавляет latency в on-device критичных путях solver/parser → tradeoff_required: true |
| observability ↔ simplicity | rich distributed tracing усложняет on-device компоненты → I20 может создать отдельную qa-задачу |
| observability ↔ cost | server-side retention для deletion audit log (legal requirement) → cost-justified, tradeoff_required: false |

Findings с `tradeoff_required: true` → I20 создаёт отдельную задачу с explicit acceptance criteria для разрешения trade-off в реализации.
